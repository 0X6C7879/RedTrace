# 业务逻辑漏洞案例集

> 整合内部真实漏洞与业界经典案例，提供实战指导

## 一、内部真实案例

### 案例1：kim客户端开放fs能力可导致任意命令执行、文件读写
**系统**: 某内部系统

**漏洞描述**:
由于 kim PC 客户端开放了 fs 能力，可通过覆盖本地文件达到任意代码执行、任意文件的读写。

**技术细节**:
- 客户端向网页层暴露了文件系统（fs）API
- 攻击者可通过该 API 覆盖本地关键文件（如可执行文件、配置文件）
- 文件覆盖后可在宿主机上达成任意代码执行效果
- 属于客户端安全与业务逻辑设计缺陷的交叉场景

**修复方案**:
对文件读写目录进行白名单限制，仅允许访问特定业务目录，禁止任意路径穿越。

**经验总结**:
业务逻辑漏洞需要从攻击者视角重新审视每个业务环节，关注异常状态流转。

### 案例2：电商客户活动未报名用户列表查询存在逻辑漏洞
**系统**: 某内部系统

**漏洞描述**:
某内部系统电商客户活动「未报名用户列表查询」接口存在越权漏洞。选择平台ID查询时，可以查询其他代理商下的平台ID信息；使用昵称或营业执照名称查询时，可返回非当前用户下的4000条数据。

**技术细节**:
- 接口 `/rest/dsp/agent/activity/board/toSignUp/v2` 缺乏严格的代理商归属校验
- 查询参数未绑定当前登录用户的代理商维度，仅做了基础的身份认证
- `fileBusType=TO_SIGN_UP_ACTIVITY_BOARD` 同样存在相同逻辑缺陷
- 属于典型的水平越权（IDOR）与逻辑校验缺失组合漏洞

**修复方案**:
后端严格校验当前用户的代理商归属，所有查询条件强制加入当前用户的代理商 ID 作为过滤条件。

**经验总结**:
状态机的状态转换需要严格限制合法的转换路径，防止跳过中间步骤。

### 案例3：Snack视频下载功能可绕过用户隐私设置
**系统**: 某内部系统

**漏洞描述**:
用户可以设置视频是否允许下载及是否为隐私用户。客户端在下载视频时先调用 `/rest/bulldog/photo/downloadPermission` 校验权限，但黑产可直接调用 `/rest/bulldog/photo/waterMark/getUrl` 绕过权限校验，获取任意视频下载链接。

**技术细节**:
- 权限校验接口与下载链接接口为两个独立端点，且两者无强关联
- 校验逻辑完全依赖客户端遵守顺序调用约定，服务端未在获取下载链接时重新验证
- 攻击者只需跳过 `downloadPermission` 接口，直接请求 `waterMark/getUrl` 即可
- 属于"前置校验与业务操作分离"的经典逻辑漏洞

**修复方案**:
在 `/rest/bulldog/photo/waterMark/getUrl` 接口内部调用 `downloadPermission` 的校验函数，将条件校验和业务逻辑在同一接口中完成，不依赖客户端的顺序调用。

**经验总结**:
优惠券、积分等数值型参数需做正负值校验，防止通过负值绕过业务逻辑。

### 案例4：某内部系统视频下载接口可绕过用户隐私设置
**系统**: 某内部系统

**漏洞描述**:
与案例3模式相同。`/rest/o/photo/downloadPermission` 校验接口与 `/rest/o/photo/waterMark/getUrl` 获取链接接口解耦，攻击者直接调用后者即可绕过下载权限校验，下载受隐私保护的视频。

**技术细节**:
- 服务端将权限校验与资源获取拆分为两个独立接口
- `waterMark/getUrl` 接口未在内部独立执行权限检查
- 任何持有有效登录态的用户均可直接请求下载链接
- 对于隐私用户的视频保护完全失效

**修复方案**:
在 `waterMark/getUrl` 接口内统一集成下载权限校验逻辑，确保权限验证在服务端完成，不信任客户端的流程控制。

**经验总结**:
并发请求可能导致幂等性问题，关键业务操作需添加分布式锁或数据库乐观锁。

### 案例5：4个接口可查询任意员工手机号、身份证号
**系统**: 某内部系统

**漏洞描述**:
招聘系统的4个接口（`/recruit/campus/api/v1/internal/open/resume/infos`、`/recruit/campus/api/v1/internal/open/candidate/get`、`/recruit/campus/api/v1/internal/open/offer/users-will-entry-new`、`/recruit/campus/api/v1/open/search/data/apply/{applyId}`）缺乏鉴权控制，可查询任意员工的手机号和身份证号等敏感个人信息。

**技术细节**:
- 接口路径中带有 `/open/` 标记，可能被误认为是公开接口而省略鉴权
- 查询参数（如 `applyId`）为可枚举或可预测的数值型标识
- 接口直接返回未脱敏的手机号和身份证号
- 涉及多个业务模块，说明鉴权设计存在系统性缺失

**修复方案**:
对所有涉及个人敏感信息的接口严格添加身份验证和权限校验，明确区分 `open`（外部公开）和内部接口的访问控制策略。

**经验总结**:
支付类接口需在服务端验证金额，不能依赖客户端传入的价格参数。

### 案例6：开放平台可利用主App service_token 获取第三方App passToken
**系统**: 某内部系统

**漏洞描述**:
可使用主 App 的 `service_token` 最终获得第三方 App 的 `passToken`。由于主 App 的 `service_token` 易于获取，此信任链传递路径存在极大的盗号风险。

**技术细节**:
- 开放平台的 token 体系中，主 App 信任凭证可被用于换取第三方 App 的用户凭证
- token 转换接口缺乏二次身份验证或 tokensig 签名保护
- 攻击者获取主 App 的 `service_token` 后，可冒充任意用户登录第三方 App
- 属于 OAuth/token 信任链设计缺陷

**修复方案**:
接入 tokensig 签名验证，确保 token 转换链路的每一步均有合法性校验，防止跨 App 的 token 滥用。

**经验总结**:
短信/邮件验证码需有使用次数限制和过期时间，防止暴力破解。

### 案例7：某内部系统接口未校验短信验证码
**系统**: 某内部系统

**漏洞描述**:
某些页面设置了短信验证码二次认证，但后续页面中的服务端业务接口未继承验证码校验逻辑，导致攻击者可跳过验证码验证，直接调用后端接口办理业务，安全机制完全失效。

**技术细节**:
- 验证码校验仅在入口页面执行，会话状态未被记录到服务端
- 后续业务接口独立运行，不验证是否已通过二次认证
- 攻击者可在获取会话 cookie 后直接调用任意业务接口
- 属于"一次性验证与持续授权"的设计脱节问题

**修复方案**:
将验证码校验结果保存到服务端 Session，在每个需要二次认证保护的接口中检查该 Session 标记是否存在且有效。

**经验总结**:
操作顺序依赖类漏洞：先绑定再修改的场景需重新校验操作合法性。

### 案例8：支付中台扫码支付接口存在骗刷风险
**系统**: 某内部系统

**漏洞描述**:
某支付系统的二维码扫码支付接口存在骗刷风险。攻击者可生成为自己购买商品的二维码，诱骗其他用户扫码支付，从而替自己完成购买。`/kQrCode/alipay` 接口同样存在相同问题。

**技术细节**:
- 二维码生成时未绑定发起用户与支付用户的关系校验
- 二维码有效期过长（或无过期限制），增大了被骗用风险
- 无 IP 限制或频率控制，可批量生成骗刷二维码
- 属于支付流程中"付款方身份与商品受益方"未绑定的业务逻辑漏洞

**修复方案**:
设置二维码默认过期时间为60秒；开启 IP 限制开关；在服务端校验扫码用户与二维码创建者的关系，限制为本人消费场景。

**经验总结**:
重放攻击防护：关键接口需校验 nonce 或 timestamp，防止请求被重放。

### 案例9：6个接口可获取全量员工手机号、身份证号等数据
**系统**: 某内部系统

**漏洞描述**:
6个员工信息查询接口（`/common/api/ssc/user/getUserByUserIdList`、`getUserByLike`、`like`、`getByUsername`、`getByUserNameList`、`getUsersByHrbp`）未做访问控制，任何内部用户均可获取公司全量员工的手机号、身份证号等敏感数据。

**技术细节**:
- 接口路径设计为通用查询服务，缺乏调用方权限校验
- 支持模糊查询（`like`、`getUserByLike`），可枚举全量数据
- 返回值包含未脱敏的手机号和身份证号等隐私字段
- 属于内部 API 的横向越权与数据过度暴露问题

**修复方案**:
基于调用方角色（HR、管理员等）限制接口权限，对返回的手机号、身份证号等敏感字段进行脱敏处理，添加访问日志与异常告警。

**经验总结**:
业务流程中的灰度功能或 A/B 分支可能存在仅部分场景鉴权的安全盲区。

### 案例10：用户恶意耗光店铺库存导致正常用户无法购买
**系统**: 某内部系统

**漏洞描述**:
在某平台小店购买货品时，单货品可无限次数下单而不付款，导致恶意用户可持续占用店铺全部库存（生成大量未付款订单），使正常用户看到的库存始终为0，无法下单购买。

**技术细节**:
- 下单接口未限制单用户同一商品的未付款订单数量
- 库存扣减逻辑基于下单时的预占机制，未区分付款意愿
- 攻击者无需付款即可无限占用库存，构成拒绝服务式业务攻击
- 属于电商系统中"库存预占无上限"的逻辑漏洞

**修复方案**:
业务方可评估增加更严格的下单限制：同一用户同一商品未付款订单数量上限、超时自动取消释放库存、下单频率限制等。

**经验总结**:
数量类参数需检查溢出，极大或极小的值可能触发业务异常或绕过限制。

## 二、业界经典案例（乌云）

### 案例1：橡果国际任意账户密码重置（验证码返回前端）
**厂商**: 橡果国际 | **类型**: 设计缺陷（验证码回显）

**洞察**: 密码找回流程中，服务端将验证码的验证结果返回给客户端，攻击者可截取响应并修改为 `true`，无需实际验证码即可重置任意账户密码。

**测试流程**:
1. 请求密码重置，输入目标手机号
2. 随意输入验证码，截取 HTTP 响应
3. 修改响应中的验证码验证结果为 `true`
4. 提交新密码完成重置

**技术细节**:
找回密码处：输入手机号发送验证码，随便输验证码，截返回的包改为 `true` 就可以重置了。

**POC示例**:
```
1. POST /resetpwd?phone=18888888888 发送验证码
2. 输入错误验证码，拦截响应
3. 将响应 {"success":false} 改为 {"success":true}
4. 系统认为验证通过，允许重置密码
```

**绕过技巧**: 修改 HTTP 响应体绕过客户端验证

**修复建议**: 验证码验证必须在服务端完成，状态不返回给客户端，客户端提交验证码让服务端验证

### 案例2：p2p金融安全之利苍贷任意密码重置（验证码绑定手机不一致）
**厂商**: 利苍贷（P2P金融）| **类型**: 设计缺陷（验证码与账号绑定缺失）

**洞察**: 密码重置流程中，验证码验证成功后的 token 与目标账号未强绑定，可先验证自己手机号获得 token，然后用该 token 重置他人账号密码。

**测试流程**:
1. 请求重置自己手机号的验证码
2. 输入正确验证码获取重置 token
3. 将 token 用于重置目标用户（不同手机号）的密码
4. 成功重置任意用户密码

**技术细节**:
`code` 参数验证成功后，token 与具体账号不绑定，可跨账号使用。

**POC示例**:
```
1. POST /resetpwd?phone=my_phone 获取验证码
2. 输入正确验证码获取token=xxxxxx
3. POST /setpwd?phone=victim_phone&token=xxxxxx&newpwd=hacked
```

**绕过技巧**: 跨账号复用验证令牌

**修复建议**: 重置 token 必须与手机号强绑定，验证 token 时校验手机号一致性

### 案例3：某连锁酒店验证码设置不当可修改用户密码（验证码在响应包中）
**厂商**: 某连锁酒店 | **类型**: 设计缺陷（验证码直接在响应中返回）

**洞察**: 密码找回发送验证码后，验证码直接出现在 HTTP 响应包中，攻击者不需要访问目标手机即可获取验证码。

**测试流程**:
1. 请求找回任意手机号密码
2. 抓取发送验证码后的 HTTP 响应
3. 从响应中直接读取验证码
4. 输入验证码修改密码

**技术细节**:
找回密码时，验证码直接在返回信息中，填入即可修改。

**POC示例**:
```
POST /api/resetpwd HTTP/1.1
{"phone":"18888888888"}

# 响应中包含: {"code":200,"sms_code":"123456"}
```

**绕过技巧**: 直接从响应读取验证码

**修复建议**: 验证码只发送到用户手机/邮件，绝不在 HTTP 响应中返回，服务端维护验证码状态

### 案例4：迅雷某客户服务系统存在缺陷可导致登录大量用户账号
**厂商**: 迅雷 | **类型**: 设计缺陷（签名算法可推导）

**洞察**: 迅雷客服系统的 sign 签名仅由 `account+timestamp` 等简单参数计算，签名算法被逆向后可伪造任意用户的签名，在几分钟内批量登录数百个账号。

**测试流程**:
1. 分析请求中的 `sign/timestamp/account` 参数
2. 逆向推导 `sign` 的计算逻辑
3. 针对目标账号构造有效 `sign`
4. 批量登录任意用户账号

**技术细节**:
`sign=MD5(account+createTime+固定密钥)` 类似，逆向算法后可伪造任意账号的签名。

**POC示例**:
```
sign计算: sign = MD5(account + timestamp + secret_key)

伪造: sign = MD5('victim@email.com' + '1442980310' + 'WeAjsn10Nin0w0vq7wPgbfbrrE')
```

**绕过技巧**: 逆向签名算法绕过身份验证

**修复建议**: 签名密钥绝不嵌入客户端，使用服务端下发的随机 nonce 参与签名，增加 HMAC 等不可逆算法

### 案例5：某手机厂商积分商城刷花瓣兑换产品
**厂商**: 某手机厂商 | **类型**: 设计缺陷（业务逻辑漏洞）

**洞察**: 积分商城兑换流程存在逻辑漏洞，通过重放或并发请求可以用少量积分兑换大量商品，涉及实际经济损失。

1. 正常发起一次兑换请求
2. 抓取兑换请求包
3. 并发发送多个相同的兑换请求
4. 或通过重放攻击多次消费同一积分

**技术细节**:
积分兑换存在竞态条件或校验缺失，可刷取花瓣兑换产品。

**POC示例**:
```
# 并发请求（竞态条件）
for i in {1..10}; do
  curl -X POST /api/exchange --data 'points=100&product_id=1' &
done
```

**绕过技巧**: 并发请求利用竞态条件

**修复建议**: 使用数据库事务和乐观锁防止竞态条件，积分扣减使用原子操作

### 案例6：安全狗最新版网站防护SQL注入Bypass
**厂商**: 安全狗 WAF | **类型**: 设计缺陷（WAF 绕过）

**洞察**: 安全狗 WAF 的 SQL 注入检测规则存在盲区，通过特殊注释组合可绕过 WAF 检测，对底层 SQL 注入漏洞的利用不受影响。

**测试流程**:
1. 发现目标使用安全狗 WAF
2. 尝试常规 SQL 注入被 WAF 拦截
3. 使用注释符变形绕过：`and/*/\*/`
4. 确认绕过成功后进行注入

**技术细节**:
安全狗 WAF 绕过：`and/*/\*/ascii%28substring%28user%28%29,1,1%29%29=114`

**POC示例**:
```
GET /page?id=1 and/*//*/ascii/*//*/substring(user(),1,1)=114-- HTTP/1.1

// 或使用
id=1 and/*/\*/ascii%28substring%28user%28%29,1,1%29%29=114
```

**绕过技巧**: 嵌套注释符 `/**/` 和 `\*/` 绕过安全狗规则

**修复建议**: （针对 WAF 厂商）改进正则规则，对嵌套注释等变形进行检测

### 案例7：WDCP后台的登录IP可被伪造（X-Forwarded-For）
**厂商**: WDCP | **类型**: 设计缺陷（IP 来源信任问题）

**洞察**: 后台登录限制基于 `X-Forwarded-For` 头判断 IP 来源，攻击者可伪造此 Header 绕过 IP 白名单限制。

**测试流程**:
1. 发现后台存在 IP 限制
2. 在请求头中添加 `X-Forwarded-For: 127.0.0.1`
3. 或 `X-Forwarded-For: 白名单IP`
4. 成功绕过 IP 限制访问后台

**技术细节**:
WDCP 后台基于 `X-Forwarded-For` 等 Header 判断登录 IP，可被客户端伪造。

**POC示例**:
```
GET /admin/login HTTP/1.1
X-Forwarded-For: 127.0.0.1
X-Real-IP: 127.0.0.1
Client-IP: 127.0.0.1
```

**绕过技巧**: 伪造 `X-Forwarded-For`/`X-Real-IP` 头绕过 IP 验证

**修复建议**: 不信任 `X-Forwarded-For` 等可伪造的 Header 作为 IP 来源，使用 TCP 连接的实际 IP 或由可信代理传递

**洞察**: 机场 WIFI Portal 认证系统存在登录绕过漏洞，通过修改请求参数可绕过付费/认证直接上网。

**测试流程**:

2. 分析认证请求的参数
3. 修改 `err_flag` 或其他状态参数
4. 绕过认证直接访问互联网

**技术细节**:
`err_flag`、`userName`、`essid`、`paramStr`、`url` 等参数控制认证流程，可被篡改绕过。

**POC示例**:


**绕过技巧**: 修改 `err_flag` 为成功状态绕过认证

**修复建议**: 认证状态在服务端维护，不信任客户端传递的状态参数

### 案例9：某记账APP任意用户密码重置（影响近8000万用户）
**厂商**: 某记账 APP | **类型**: 设计缺陷（密码重置无手机号校验）

**洞察**: 密码重置接口仅验证 token 有效性，未校验 token 与目标账号的绑定关系，可用自己的有效 token 重置任意账号密码，影响近 8000 万用户。

**测试流程**:
1. 用自己账号发起密码重置获取 token
2. 修改重置请求中的用户标识为目标用户
3. 使用自己的有效 token 提交
4. 成功重置他人密码

**技术细节**:
近 8000 万用户面临任意密码重置风险，token 与 uid 未做绑定验证。

**POC示例**:
```
POST /api/resetpwd HTTP/1.1

{"uid":"victim_uid","token":"my_valid_token","new_pwd":"hacked123"}
```

**绕过技巧**: token 与 uid 未绑定验证

**修复建议**: token 必须与申请时的 uid 强绑定，重置时必须校验 token 对应的 uid 与请求 uid 一致

### 案例10：某通信厂商某重要站点存在任意密码重置漏洞
**厂商**: 某通信厂商 | **类型**: 设计缺陷（密码重置流程缺陷）

**洞察**: 密码重置功能的多步骤流程中，步骤间缺乏状态验证，可直接跳过验证步骤到达最终重置密码页面。

**测试流程**:
1. 启动密码重置流程
2. 不完成验证步骤，直接跳转到重置密码 URL

4. 直接提交新密码完成重置

**技术细节**:
密码重置多步流程缺乏步骤验证，可越步访问最终重置页面。

**POC示例**:
```
直接访问 /resetpwd/step3?userid=victim_id&new_password=hacked
（跳过step1验证码和step2身份核实）
```

**绕过技巧**: 直接跳过验证步骤

**修复建议**: 每个步骤必须验证前置步骤是否完成，使用服务端 Session 记录流程状态

## 三、方法论总结

### 3.1 高频参数统计

| 参数名 | 出现频次 | 典型场景 |
|--------|----------|----------|
| `token` | 5次 | 密码重置 token 与用户未绑定 |
| `phone` / `userId` / `uid` | 5次 | 目标账号标识，可替换为任意值 |
| `err_flag` / `success` | 3次 | 前端状态参数，可被篡改 |
| `X-Forwarded-For` | 2次 | IP 白名单绕过 |
| `sign` / `timestamp` | 2次 | 可逆签名算法伪造身份 |
| `downloadPermission` | 2次 | 前置校验接口被绕过 |
| `applyId` / `agentId` | 2次 | 可枚举的资源标识 |

### 3.2 攻击模式分布

| 攻击模式 | 案例数 | 典型案例 |
|----------|--------|----------|
| **密码重置流程缺陷** | 5个 | 验证码回显、token 未绑定账号、步骤越过 |
| **前置校验被绕过** | 3个 | 下载权限校验分离、短信验证码校验未传递 |
| **客户端状态可篡改** | 3个 | 响应包修改、IP 头伪造、portal 参数篡改 |
| **竞态条件/重放** | 2个 | 积分刷取、库存耗尽 |
| **越权数据访问** | 2个 | 代理商隔离缺失、员工信息越权查询 |
| **信任链设计缺陷** | 2个 | token 跨 App 复用、签名算法可逆 |
| **客户端暴露危险能力** | 1个 | 文件系统 API 未限制路径 |

### 3.3 关键检测信号

1. **密码找回接口**：检查验证码是否出现在响应包中；检查 token 是否与目标账号强绑定；检查多步骤流程是否有服务端状态机保护
2. **分离的校验+业务接口**：检查业务执行接口是否可被独立调用并跳过前置校验接口
3. **IP 限制实现**：检查是否基于可伪造的 HTTP Header（`X-Forwarded-For`、`X-Real-IP`）进行 IP 判断
4. **积分/库存类操作**：检查是否存在并发竞态条件；是否使用数据库原子操作
5. **客户端签名**：检查签名算法是否可逆推导；密钥是否硬编码在客户端
6. **状态参数**：检查认证状态、流程状态是否由客户端传递，服务端是否盲目信任
7. **内部 API 路径**：含 `/open/`、`/internal/` 的接口是否真正添加了权限校验

### 3.4 常见绕过技巧

1. **响应包篡改**：截取并修改服务端响应（`false` → `true`，`0` → `1`），绕过客户端逻辑判断
2. **Token 跨账号复用**：使用自己账号获取的有效 token，替换请求中的目标 uid 重置他人密码
3. **步骤越过（Force Browsing）**：直接访问多步骤流程的最终 URL，跳过中间验证步骤
4. **伪造 IP 头**：在请求中注入 `X-Forwarded-For: 127.0.0.1` 绕过 IP 白名单限制
5. **并发竞态（Race Condition）**：并发发送多个相同请求，利用数据库锁缺失实现超额消费
6. **接口直接调用**：跳过客户端规定的调用顺序，直接请求业务执行接口绕过前置校验
7. **参数替换越权**：修改请求中的用户标识参数（uid、agentId、phone）访问他人资源
8. **客户端签名逆向**：分析并逆向推导签名算法，伪造任意用户的合法签名
