## 一、内部真实案例

### 案例1：Redis任意键写入
**系统**: 某内部系统

**漏洞描述**:
Redis任意键写入漏洞是指攻击者通过不安全的 Redis 配置或接口，向 Redis 数据库写入恶意数据，可能导致敏感数据被篡改、覆盖，甚至可能进一步利用 Redis 的功能（如写入恶意代码、执行命令）来攻击服务器或其他服务。这类漏洞通常与 Redis 的未授权访问、弱口令或命令权限控制不足相关。

**技术细节**:
- Redis 未绑定本地地址，直接暴露在网络中（默认监听 0.0.0.0:6379）
- 未配置 requirepass 密码认证，或使用弱口令
- 危险命令（CONFIG、FLUSHALL、SAVE）未被禁用或重命名
- 攻击者可利用 CONFIG SET dir/dbfilename 将恶意内容写入 crontab、SSH authorized_keys 等文件，进一步实现 RCE

**修复方案**:
1. 绑定本地地址：`bind 127.0.0.1`，通过防火墙限制公网访问
2. 启用强密码认证：`requirepass <复杂密码>`
3. 禁用危险命令：通过 `rename-command` 将 FLUSHALL、CONFIG、SHUTDOWN、SAVE、DEBUG 重命名为空字符串
4. Redis 6.0+ 启用 ACL 用户权限控制，为业务账号分配最小权限

**经验总结**:
CORS 配置需精确指定允许的域名，禁止使用通配符（*）或直接反射请求的 Origin 头

### 案例2：账号风控配置有误可任意登录泄漏商家后台
**系统**: 某内部系统

**漏洞描述**:
黑产模拟：真实业务数据窃取红蓝对抗。黑产通过社工库获取可登录的商家账号密码，登录后抓取商家订单信息（挂代理），包含收件人、电话号码、收件地址、购买商品等要素信息，用于检验防爬策略、高敏感信息隐藏策略的有效性，判断商家侧综合安全策略是否可靠。

**技术细节**:
- 账号风控策略配置错误，未能有效识别异常登录行为（代理 IP、账号撞库）
- 缺乏有效的防爬机制，批量数据可在短时间内被抓取
- 商家后台高敏感信息（手机号、地址）未做脱敏处理
- 登录行为无频率限制或限制规则存在绕过

**修复方案**:
修复风控配置，加强登录异常检测、IP 频率限制及敏感数据脱敏展示

**经验总结**:
Nginx/Apache 等 Web 服务器的目录遍历（autoindex）在生产环境必须关闭

### 案例3：中控门禁智慧系统-越权漏洞
**系统**: 某内部系统

**漏洞描述**:
中控门禁智慧系统越权漏洞，涉及接口：`/authUser.do`、`/api/person/*`（4个）、`/api/door/remote*`（4个）、`/api/card/getCards/{pin}`、`/api/department/*`（3个），上述接口缺乏有效的认证和授权校验，攻击者可越权访问或控制门禁设备。

**技术细节**:
- 接口入口缺少认证校验，可未授权访问用户/部门/门禁信息
- 带资源标识（id/pin/设备ID）的请求未做对象级授权（IDOR），可跨租户/用户访问
- 闸机远程控制接口（`/api/door/remote*`）无操作审计和频率限制，存在滥用风险
- 缺少 RBAC 权限点校验，普通用户可访问管理员级接口

**修复方案**:
对上述接口统一补齐服务端访问控制：接口入口做认证 + RBAC 权限点校验，所有带资源标识（id/pin/设备ID）的请求必须做对象级授权（资源归属/租户/ACL/管理范围）校验，采用默认拒绝与最小权限策略；对闸机远程控制等高危操作增加审计与限流。

**经验总结**:
未使用的端口、服务、功能应在生产环境关闭，减少攻击面

### 案例4：任意文件下载
**系统**: 某内部系统

**漏洞描述**:
任意文件下载漏洞（Arbitrary File Download Vulnerability）是指攻击者通过构造恶意请求，未经授权下载服务器上的敏感文件（如配置文件、数据库备份文件、代码文件等），从而导致信息泄露的安全漏洞。

**技术细节**:
- 文件下载接口直接将用户输入拼接为文件路径，未做路径标准化（realpath）
- 未过滤 `../` 目录穿越字符，可跳出合法目录访问任意文件
- 未限制可下载文件类型，`.env`、`.config`、数据库备份等敏感文件均可下载
- 接口未做身份认证与权限校验，任何人可访问

**修复方案**:
1. 白名单机制：仅允许下载特定目录下的特定类型文件
2. 路径标准化：对用户传入路径使用 realpath 处理，过滤 `../` 等穿越字符
3. 文件映射机制：通过文件 ID/哈希值映射真实路径，不暴露真实路径
4. 严格身份验证与授权校验，确保只有授权用户可下载

**经验总结**:
云存储桶（OSS/S3）需关闭公开读写权限，通过签名 URL 控制访问

### 案例5：JWT对称密钥可被破解最终实现任意用户登录
**系统**: 某内部系统

**漏洞描述**:
某云直播平台 JWT 使用 HS256（对称加密）算法签名。攻击者使用 44G GPU 进行离线暴力破解，不到 2 天时间成功破解线上 JWT HS256 密钥。拿到 JWT key 后可伪造任意用户 token，最终实现任意用户登录。

**技术细节**:
- JWT 使用 HS256 对称算法，密钥强度不足，可被 GPU 暴力破解
- 一旦密钥泄露，攻击者可为任意 sub（用户ID）伪造有效 token
- 对称算法密钥同时用于签发和验证，服务端无法区分合法与伪造 token
- 未设置 token 有效期或有效期过长，扩大了被利用的时间窗口

**修复方案**:
更换 JWT 加密算法为非对称加密算法（如 RS256/ES256），使用私钥签发、公钥验证，即使公钥泄露也无法伪造 token

**经验总结**:
Kubernetes 的 RBAC 需遵循最小权限原则，避免使用 cluster-admin 角色

### 案例6：智齿客服系统-网络权限风险
**系统**: 某内部系统

**漏洞描述**:
智齿客服系统三台服务器（10.251.2.191、10.251.2.196、10.251.2.205）均存在极宽泛的网络策略，该策略可通外网、任意 IDC、任意端口，相当于完全开放的出站规则，存在数据外传和内网横向移动风险。

**技术细节**:
- 网络策略配置为 `0.0.0.0/0`，允许访问任意外网地址和端口
- 宽泛策略可被利用作为跳板，访问外部 C2 服务器或进行数据外传
- 同时可通任意 IDC，存在内网横向移动风险
- 缺少出站流量审计，异常访问行为无法被及时发现

**修复方案**:
1. 梳理业务所需外网访问目标及端口，将 `0.0.0.0/0` 策略收紧为白名单模式
2. 先开启流量审计，观察 1-2 周后再实施封禁，避免误伤业务

**经验总结**:
内部调试端点（/debug、/metrics、/health）需在外网访问时鉴权或限制 IP

### 案例7：测试接口未下线
**系统**: 某内部系统

**漏洞描述**:
`AiasFacadeController` 下全部的测试接口未下线，`QueueController` 下的 `/queue/nextQueueId` 接口未下线。测试接口通常缺乏安全校验、可能暴露敏感业务逻辑或内部数据，在生产环境遗留存在安全隐患。

**技术细节**:
- 测试接口通常跳过认证、权限校验，直接暴露业务逻辑
- `/queue/nextQueueId` 可能暴露队列 ID 生成规则，辅助业务逻辑攻击（如预测 ID、枚举资源）
- 开发阶段为调试方便创建的接口，发布时未纳入安全上线检查流程

**修复方案**:
下线所有测试接口，在 CI/CD 流程中增加测试接口扫描检查，上线前必须移除或禁用调试/测试端点

**经验总结**:
TLS 证书需定期更新，且应配置 HSTS 头防止协议降级攻击

### 案例8：EHR电子档案系统-网络权限风险
**系统**: 某内部系统

**漏洞描述**:
EHR 电子档案系统正式/测试环境均存在极宽泛策略：可出网、通 IDC 任意主机和端口，疑似将兜底拒绝规则（deny all）配置反向，导致出站流量完全不受限制，需收敛网络权限至业务所需范围和端口。

**技术细节**:
- 正式与测试环境共享了同样的宽泛网络配置，测试环境风险蔓延至生产
- 网络策略逻辑配置错误（default allow 替代了 default deny），导致所有出站流量放行
- 员工可通过该系统向外传输敏感 HR 数据
- 缺乏出站流量监控，内鬼或供应链攻击难以察觉

**修复方案**:
收敛网络权限至业务所需范围和端口，正确配置默认拒绝（default deny）策略，正式/测试环境分离网络隔离

**经验总结**:
数据库不应直接暴露在公网，必须通过 VPC/防火墙规则限制访问范围

### 案例9：Tomcat Manager密码爆破 & CVE-2017-12615任意文件写入
**系统**: 某内部系统

**漏洞描述**:
通过用户名枚举获取到三个账号（tomcat、admin、zhangliyao），Tomcat Manager 密码存在暴力破解风险。同时存在 CVE-2017-12615（Tomcat 任意文件写入漏洞），攻击者可通过 PUT 方法上传 JSP webshell，实现远程代码执行。

**技术细节**:
- Tomcat Manager 未限制 IP 访问，且使用弱口令，可被暴力破解
- CVE-2017-12615：Tomcat 在 Windows 环境下，HTTP PUT 方法未被禁用，可通过 `PUT /shell.jsp%20` 绕过扩展名过滤上传 JSP 文件
- Manager 账户一旦被攻破，可直接部署 WAR 包 Getshell

**修复方案**:
限制 Tomcat Manager 仅本地访问，设置强密码，禁用 HTTP PUT 方法，升级至修复版本（7.0.81+/8.0.45+/8.5.23+），以及删除默认账号

**经验总结**:
容器运行时需以非 root 用户运行，并限制容器的能力集（capabilities）

### 案例10：部分内网系统可公网访问
**系统**: 某内部系统

**漏洞描述**:
由于配置错误（未配置 TOA 模块），导致未能正确判断源 IP，相当于部分系统的部分流量允许公网访问。原本仅限内网访问的系统通过公网 IP 可直接访问，绕过了基于 IP 的访问控制策略。

**技术细节**:
- TOA（TCP Option Address）模块未安装，导致真实客户端 IP 无法正确透传和识别
- 基于源 IP 的访问控制策略失效，内网系统对公网暴露
- 攻击者可直接访问原本只能内部访问的管理后台、API 接口等高权限系统

**修复方案**:
安装 TOA 模块，确保源 IP 正确识别；同时梳理内网系统的网络访问控制规则，添加多层防护，不仅依赖 IP 判断

**经验总结**:
安全相关的 HTTP 响应头（CSP、X-Frame-Options、X-XSS-Protection）需正确配置

## 二、业界经典案例（乌云）

### 案例1：某社交平台某服务配置不当导致任意文件读取
**厂商**: 某社交平台 | **类型**: 系统/服务运维配置不当（文件读取）

**洞察**: 服务配置不当暴露了包含 root 账号 hash 和 SVN 账号密码的文件，从 `/etc/shadow` 可读取密码 hash，进一步可离线暴力破解

**测试流程**:
1. 发现配置错误暴露的服务
2. 读取 `/etc/shadow` 获取密码 hash
3. 收集 SVN 账号密码
4. 离线破解 hash 或利用泄露凭证

**技术细节**:
配置不当导致文件读取：`root:*:15240`，员工 SVN 账号密码泄露

**POC示例**:
```
curl http://target/exposed_service/../../../etc/shadow
```

**绕过技巧**: 无（配置错误直接可达）

**修复建议**: 检查服务配置，禁止对外暴露，最小化文件系统访问权限

### 案例2：PPTV游戏某站配置不当导致Shell/入内网（phpMyAdmin + mantis）

**洞察**: 服务器目录浏览暴露 mantis 缺陷追踪系统（1.2.19 版本含漏洞）和 phpMyAdmin，phpMyAdmin 可直接操作数据库

目录遍历发现 mantis-1.2.19 和 phpMyAdmin，phpMyAdmin 可执行 SQL 命令或利用 `INTO OUTFILE` 写 shell

**POC示例**:
```
GET http://target:8888/ HTTP/1.1

http://target:8888/phpmyadmin/
```

**绕过技巧**: 无

**修复建议**: 管理工具（phpMyAdmin/mantis 等）禁止外网访问，升级到最新版本，强密码保护

### 案例3：逐浪CMS特定版本疑似存在一个鸡肋后门（上传接口）

### 案例6：某快递公司速运DNS域传送漏洞
**厂商**: 申通快递 | **类型**: 系统配置不当（DNS域传送）

**洞察**: DNS 服务器未限制 zone transfer，攻击者可从 NS 服务器获取完整的内部 DNS 记录，暴露所有内网主机名和 IP 地址

**测试流程**:
1. 查询目标域的 NS 服务器
2. 对 NS 服务器执行域传送请求
3. 获取完整域名/IP 对应列表
4. 从中发现内网服务器地址

**技术细节**:
`dig axfr @ns3.diyixian.com sf-express.com` 返回完整 DNS 区域文件

**POC示例**:
```
dig axfr @ns3.diyixian.com sf-express.com
# 或: nslookup
> server ns3.diyixian.com
> ls -d sf-express.com
```

**绕过技巧**: 无（DNS 服务器未限制 AXFR 请求来源）

**修复建议**: DNS 服务器限制 zone transfer 只允许授权从服务器访问，使用 ACL 限制

### 案例7：重钢集团投票系统权限设置不当可直接下载网站源码甚至脱库
**厂商**: 重钢集团 | **类型**: 系统配置不当（Web根目录权限）

**洞察**: Web 服务器权限配置不当，允许直接下载 PHP 源码，源码中包含数据库 root 账号密码，进一步可脱库

**测试流程**:
1. 发现 Web 服务器可直接访问源码（PHP 文件以文本形式返回而非执行）
2. 下载 `index.php` 等文件
3. 从源码中提取数据库配置
4. 连接数据库获取所有数据

**技术细节**:
服务器权限配置不当，源码直接下载，数据库配置：`$DBUSER='root'; $DBPWD='';`

**POC示例**:
```
GET /config.php HTTP/1.1
# 响应返回PHP源码（而非执行结果）
# 提取: $DBUSER='root'; $DBPWD='';
```

**绕过技巧**: 配置错误无需绕过

### 案例8：北京电视台某业务平台远程命令执行（JBoss配置不当）

**绕过技巧**: JBoss 默认无认证，直接利用

## 三、方法论总结

### 3.1 高频参数统计

从以上案例中，配置错误类漏洞涉及的高频配置项如下：

| 配置项 | 出现频次 | 典型风险 |
|--------|----------|----------|
| 服务监听地址（bind/listen） | 5 | Redis/MongoDB/JBoss 绑定 0.0.0.0，对外暴露 |
| 访问认证（auth/password） | 5 | 无密码或默认凭证（weblogic/weblogic、admin/admin） |
| 网络出站规则（ACL/Security Group） | 3 | 极宽泛策略 0.0.0.0/0，允许任意出站 |
| 目录遍历开关（autoindex/Options） | 2 | Nginx/Apache autoindex on 暴露源码 |
| 危险命令/接口开放 | 3 | Redis CONFIG/FLUSHALL、JBoss invoker、Tomcat PUT |
| 测试/调试接口 | 2 | 未下线的测试接口暴露内部业务逻辑 |
| DNS zone transfer 限制 | 1 | 未限制 AXFR 来源，内部 DNS 全量泄露 |

### 3.2 攻击模式分布

```
未授权访问（无认证保护）      ████████████  6 例  （Redis、MongoDB、JBoss、phpMyAdmin、门禁系统、TOA缺失）
默认/弱凭证                  ████████      4 例  （Weblogic、Tomcat、家庭网关、JWT弱密钥）
信息泄露（源码/配置/DNS）     ██████        4 例  （目录遍历×2、DNS传送、PHP源码下载）
网络隔离不足                 ████          3 例  （智齿客服宽泛策略、EHR宽泛策略、内网公网可达）
遗留接口/后门                ████          2 例  （测试接口未下线、CMS隐藏上传接口）
```

**核心规律**：
- 配置错误漏洞 **60%+ 无需任何绕过技巧**，直接访问即可利用
- 中间件/数据库服务（Redis、MongoDB、Weblogic、JBoss）是配置错误的重灾区
- 网络边界配置（防火墙、安全组、VPC）缺失是内网系统对外暴露的根本原因

### 3.3 关键检测信号

**服务端口扫描信号**:
- 27017（MongoDB）、6379（Redis）、7001（Weblogic）、8080（JBoss/Tomcat）对外开放
- DNS 服务器响应 AXFR 请求返回完整区域记录

**HTTP 响应特征信号**:
- 响应包含 `Index of /`（目录遍历开启）
- PHP 文件以 `text/plain` 返回源码（PHP 解析器未启用）
- 访问 `/invoker/JMXInvokerServlet` 返回 200（JBoss 未授权）
- 访问管理控制台 `/console`、`/manager` 无认证或默认凭证可登录

**配置文件泄露信号**:
- 可访问 `.env`、`config.php`、`application.properties`、`redis.conf` 等配置文件
- 源码中硬编码数据库密码、密钥等敏感信息

**网络行为信号**:
- 内网服务通过公网 IP 直接可达（无 IP 白名单限制）
- 服务器可无限制访问任意外网地址（出站规则 0.0.0.0/0）

### 3.4 常见绕过技巧

> 注：配置错误类漏洞大多**无需绕过**，主要通过直接访问和默认凭证利用。以下为少数需要技巧的场景：

| 绕过场景 | 技巧说明 |
|----------|----------|
| 文件下载路径过滤 | 使用 `../`、`..%2f`、`%2e%2e/` 等编码绕过路径校验 |
| Tomcat 文件上传扩展名过滤 | 利用 CVE-2017-12615：`PUT /shell.jsp%20` 或 `/shell.jsp::$DATA`（Windows） |
| CMS 隐藏上传接口 | 通过源码审计或目录爆破发现隐藏路径（如 `uploadsss.php`） |
| IP 白名单绕过 | 通过 X-Forwarded-For、X-Real-IP 伪造头部（需服务端信任该头部） |
| JWT 密钥破解 | 离线暴力破解（HS256 弱密钥），使用 hashcat/john 加 GPU 加速 |
| 默认凭证枚举 | 针对各中间件维护默认凭证字典：weblogic/weblogic、admin/admin、tomcat/tomcat 等 |
