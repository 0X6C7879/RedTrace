# SAST Audit 模式 - CodeQL 告警研判

审计 CodeQL 扫描的安全告警数据流，判定其有效性。

---

## 判定标准

> 本模式仅输出 **vulnerability / safe / unknown** 三种结论，不输出 risk-a/risk-b。
> 判定标准基础见 SKILL.md「通用安全判定标准」，以上述范围为准。

| 结论 | 定义 | 判定条件 |
|------|------|----------|
| **vulnerability** | 代码有问题 + 数据流可追踪 + 无有效防护 | 存在危险写法 + 数据流可追踪到入口 + 无有效防护措施 |
| **safe** | 无危险写法或有有效防护 | 无危险写法，或有参数化/类型约束/白名单等有效防护 |
| **unknown** | 关键代码缺失或数据流不完整 | 关键代码不可访问，或数据流不完整 |

---

## 研判流程

### Step 1: JSON 预处理与语言识别

**触发条件**: 收到 CodeQL JSON 报告

**必做动作**:
1. 解析 vul_type → 按 vul_type 映射表映射到漏洞类型
2. 解析 url_path → 判断框架类型（grpc → gRPC，其他 → REST）
3. 解析 full_call_stack → 提取数据流路径
4. 识别编程语言（从文件扩展名/配置文件/sink API 特征）
5. 验证 url_path 与实际代码的一致性

**vul_type 映射表**:

| JSON vul_type | 漏洞类型 | 加载文档 |
|--------------|---------|----------|
| `SQL_Injection_*` | SQLi | `references/{lang}/{lang}-sql-injection.md` |
| `Command_Injection` / `Expression_Injection` | RCE | `references/{lang}/{lang}-rce.md` |
| `Deserialization` | Deserialization | `references/{lang}/{lang}-deserialization.md`（Java/Python）或 `references/{lang}/{lang}-rce.md`（Go/JavaScript） |
| `SSRF_*` / `py/ssrf` | SSRF | `references/{lang}/{lang}-ssrf.md` |
| `Path_Traversal_*` | PathTraversal | `references/{lang}/{lang}-path-traversal.md` |
| `XSS_*` / `Reflected_XSS` / `Dom Based XSS` / `js/react-xss-dom` / `js/vue-xss-dom` / `js/xss-postmessage` / `java-FileWriteToResp` | XSS | `references/{lang}/{lang}-xss.md` |
| `Open_Redirect_*` / `Unvalidated_Redirect` | OpenRedirect | `references/{lang}/{lang}-open-redirect.md` |
| `XXE` / `Xml_External_Entity` | XXE | `references/{lang}/{lang}-xxe.md` |
| `FileUpload` / `FileUpload_Cloud` / `set_MIME` | FileUpload | `references/{lang}/{lang}-file-upload.md` |
| `unvalidated-cors-origin-set` / `cors-misconfiguration-for-credentials` | CORS | `references/{lang}/{lang}-cors.md` |
| `MISSING_AUTHENTICATION` / `MISSING_AUTHORIZATION` / `MISSING_PERMISSION_CHECK` | BrokenAccessControl | `references/{lang}/{lang}-broken-access-control.md` |
| `Private_Account_Access` / `Visibility_Bypass` / `private_account` | PrivateAccount | `references/{lang}/{lang}-private-account.md` |
| `Private_Video_Leak` / `private_video` / `private_video_grpc` | PrivateVideo | `references/{lang}/{lang}-private-video.md` |
| `Expression_Language_Injection_OGNL` / `Expression_Language_Injection_SPEL` / `QLExpress` | RCE | `references/{lang}/{lang}-rce.md` |
| `swagger` / `js/swagger` | SwaggerMisconfig | `references/{lang}/{lang}-swagger-misconfig.md` |
| `Python_web_enable_debug` | WebEnableDebug | `references/python/python-web-enable-debug.md` |

> {lang} 从本 Step 识别的编程语言替换。文件上传规则仅支持 Java/Python/Go；CORS 规则仅支持 Java/JavaScript；WebEnableDebug 仅支持 Python；私密视频越权仅支持 Java。

**full_call_stack 解析**：JSON 数组，每元素含 `file`/`line`/`code`/`method`（可选），按顺序拼接为 `[文件:行号] 变量名 → ...`。

**框架类型验证逻辑**:

| CodeQL url_path | 验证动作 | 实际代码特征 | 最终判定 |
|----------------|---------|-------------|---------|
| `grpc` | 搜索 gRPC 注解和基类 | 存在 @KrpcService/@GrpcService | gRPC |
| `grpc` | 搜索 gRPC 注解和基类 | 存在 @RestController/@Controller | **REST（自动修正）** |
| 非 grpc | 搜索 gRPC 注解和基类 | 存在 @KrpcService/@GrpcService | **gRPC（自动修正）** |
| 非 grpc | 搜索 gRPC 注解和基类 | 存在 @RestController/@Controller | REST |

**验证命令**:
```bash
# 搜索 gRPC 特征
grep -n "@KrpcService\|@GrpcService\|extends.*ImplBaseV2\|extends.*ServiceImplBase" {dest_file}

# 搜索 REST 特征
grep -n "@RestController\|@Controller\|@.*Mapping" {dest_file}
```

**输出格式**:
```
[MODE] SSRF / REST / java
[FRAMEWORK_VALIDATION] CodeQL报告: url_path="grpc", 实际代码: @GetMapping - 已自动修正为REST
```

**结束门槛**:
- 成功识别语言和框架（已验证一致性） → 进入 Step 2
- JSON 关键字段缺失 → 判定为 unknown，输出 JSON

**输出**: `[MODE] {漏洞类型} / {框架类型} / {语言}`

### Step 2: 项目上下文识别

**触发条件**: Step 1 已完成语言识别

**必做动作**:
1. 识别项目名称、项目类型、技术栈
2. 识别接口功能

**结束门槛**:
- 完成上下文识别 → 进入 Step 3

**输出**: `[CONTEXT] {项目名称} / {项目类型} / {技术栈} / {接口功能}`

### Step 3: 加载对应文档

**触发条件**: Step 2 已完成上下文识别

**必做动作**:
1. 加载 references/{lang}/{lang}-{漏洞类型}.md（**必须实际读取文件内容，不得跳过**）
2. 根据需要加载 references/common/*.md；漏洞类型为 SSRF 时，**必须加载 references/common/ssrf-proxy.md**
3. gRPC 框架加载 references/common/grpc.md

**结束门槛**:
- 成功加载所有必需文档，并输出 `[DOC_LOADED] {文件路径}` 确认 → 进入 Step 4
- 文档缺失 → 判定为 unknown，输出 JSON

**禁止**:
- 跳过语言规则文档加载
- 仅凭文档路径推断内容（必须实际读取）

### Step 4: 初始证据提取

**触发条件**: Step 3 已加载对应漏洞类型文档

**必做动作**:
1. 从 source_code 解析变量类型
2. 从 dest_code 识别危险 API
3. 从 full_call_stack 提取传播路径
4. 记录关键代码位置（文件路径、行号）
5. **Sink 语义验证**：区分"执行型"与"生成型" sink，仅执行型 sink 构成漏洞

**Sink 语义验证**：

| Sink 类型 | 识别方法 | 判定 |
|-----------|----------|------|
| SQL 执行型 | 搜索 execute/update/query/batchUpdate 调用点 | 有执行 = 真 sink |
| SQL 生成型 | 仅 append/concat 字符串，无 execute 调用 | 生成型 = 非漏洞 sink |
| 文件写入型 | 搜索 Files.write/new FileOutputStream/FileWriter 调用点 | 有写入 = 真 sink |
| 文件路径型 | 仅 resolve/getPath 拼接路径，无写入调用 | 路径型 = 非漏洞 sink |

验证命令：
```bash
# 搜索 SQL 执行点
grep -rn "execute\|update\|query" --include="*.java" {source_file_dir}
# 搜索文件写入点
grep -rn "Files.write\|FileOutputStream\|FileWriter" --include="*.java" {source_file_dir}
```

输出格式：`[SINK_VERIFY] {sink位置} | {类型: 执行型/生成型} | {是否真正执行} | {结论}`

#### Step 4.3: Sink 语义验证增强（路径遍历类必做）

**触发条件**: 漏洞类型为 path-traversal/java-path-traversal

**必做动作**:

当 sink 为文件操作 API 时，必须检查最终参数是否包含硬编码安全数据：

| 模式 | 示例 | 安全语义 |
|------|------|----------|
| 硬编码文件名 | `path.resolve("content.lines.txt")` | 攻击者只能读取特定名称文件 |
| 硬编码扩展名 | `path + ".json"` | 限制文件扩展名 |
| 双重硬编码 | `baseDir.resolve(userInput).resolve("config.txt")` | 需同时控制路径和文件名 |

**验证方法**：
1. 追溯 sink 点参数的完整构建链
2. 识别哪些部分是硬编码常量，哪些是用户可控变量
3. 判断硬编码部分是否构成有效限制

**关键判定规则**：
- 文件名完全硬编码 → 安全（终止）
- 扩展名硬编码为非敏感格式（.json/.txt/.log）→ 安全（终止）
- 仅目录路径可控，文件名硬编码 → 安全（终止）
- 路径和文件名均用户可控 → 继续分析

**真实误报案例**：

| 项目 | 告警类型 | 误判根因 | 正确判定 |
|------|---------|---------|---------|
| outlines | Absolute_Path_Traversal | 仅关注 fileId 可控，遗漏 `resolve(CONTENT_LINES_TXT)` 硬编码文件名限制 | safe |

输出格式：`[SINK_VERIFY] {sink} | 硬编码部分: {值} | 用户可控部分: {前缀/后缀/不可控} | 判定: safe/需继续分析`

**结束门槛**:
- 路径遍历类且判定为 safe → 跳过后续步骤，直接输出 JSON（硬编码限制构成有效防护）
- 其他情况 → 进入 Step 4.1

**禁止**:
- 路径遍历类跳过硬编码安全数据检查

### Step 4.5: Source 实际来源验证（强制门禁）

**触发条件**: Step 4 已完成初始证据提取

**核心问题**: CodeQL 标记的 source 仅为"代码层入参"，并非"实际数据来源"。FP 高发场景：source 为 JSON 字段、Model 字段、DTO 字段时，其值可能来自 DB/Kconf/服务间调用，而非外部用户输入。

**必做动作**:

1. **追溯 source 变量的实际写入路径**：

   | source 形态 | 追溯方法 | 来源分类 |
   |------------|----------|----------|
   | `@RequestParam`/`@PathVariable`/POST body 直接入参 | 入口即写入点 | **HTTP 外部入口** |
   | `@KrpcMethod` gRPC 直接入参 | 入口即写入点 | **gRPC 外部入口** |
   | Model/DTO 字段（如 `model.params`、`record.coverUrl`） | grep 该字段所有 setter/builder/构造调用 | 取决于实际写入点 |
   | DAO/Repository 查询结果 | 默认 DB | **DB 查询**（trusted-sources §1） |
   | `kconf.getString()`/`@Kconfig` | 配置中心 | **Kconf**（trusted-sources §2） |
   | `SessionContext.getXxx()` | 网关注入 | **会话上下文**（trusted-sources §3） |
   | 服务间 RPC 返回值 | 内部服务 | **内部服务调用** |

2. **跨接口数据流识别**（FP 高发）：

   当 source 为 Model/DTO/JSON 字段时，sink 接口不直接接收外部输入，该字段的值可能由其他接口写入 DB 后再读取。必须追溯：
   - 该字段在哪些接口被写入（grep setter/builder/构造调用）？
   - **写入接口是否有外部 HTTP/gRPC 入口**？
   - 写入接口是否对该字段做了校验/限制？
   - 字段是否为系统补全字段（参照 trusted-sources.md 第 7 节字段名模式列表）？

   ```java
   // 典型误判场景：字段名称暗示"声明在 DTO 中用户可控"
   // ExcelRecord.coverUrlMap → 在 DTO 中声明 → 误判为用户可传入
   // 实际：由 VideoApiClient 服务端补全 → 用户在请求中不传入此字段
   ```

   ```
   场景示例：
     接口 A (gRPC create): CrcMlModelCreateRequest.deploy_key → 写入 model.params (DB)
     接口 B (Deploy)     : 读取 model.params → 拼接路径 → bs3.putObject()
   
   分析路径：
     - sink 在接口 B，但 source 实际写入点在接口 A
     - 必须分析接口 A 是否对 deploy_key 有校验
     - 若 A 有白名单/格式校验 → B 的 sink 实际不可控 → safe
     - 若 A 无任何校验且对外暴露 → 间接污染成立 → 继续研判
   ```

3. **检索命令**：
   ```bash
   # 字段所有写入点
   grep -rn "\.set{FieldName}\|\.{fieldName}(" --include="*.java"
   # 字段所有 builder
   grep -rn "{FieldName}(" --include="*.java"
   # DAO 查询返回该字段
   grep -rn "Dao\|Repository\|Mapper" --include="*.java" | grep -i "{fieldName}"
   ```

**强制输出**（不输出此标签则不能进入 Step 5）:
```
[SOURCE_ORIGIN] source: {变量名} | 直接形态: {RequestParam/Model字段/...} | 实际来源: {HTTP外部/gRPC外部/DB查询/Kconf/会话/内部服务/JSON字段需追溯} | 写入侧校验: {有/无/不适用} | 可控性: {外部可控/不可控/受限可控}
```

**结束门槛**:
- 实际来源为 DB/Kconf/会话上下文，且无证据表明写入侧允许任意外部写入未校验数据 → 直接判定 safe，跳到 Step 6.5 输出 JSON
- 实际来源为内部服务调用且调用方受控 → 判定 risk-a 或 safe
- 实际来源为外部入口（HTTP/gRPC）→ 进入 Step 4.1 继续分析
- 跨接口场景且写入侧有有效校验 → 判定 safe
- 跨接口场景且写入侧无校验或不可达 → 进入 Step 4.1

**禁止**:
- 仅凭 CodeQL 标记的 source 直接判定可控性
- 看到 Model/DTO 字段就默认"用户可控"，未追溯实际写入路径
- **混淆"代码层声明"与"运行时实际来源"：字段声明在 DTO 中 ≠ 用户在请求中传入该字段**
- 跨接口场景仅分析 sink 侧接口，遗漏 source 写入侧接口的校验
- 看到字段名包含 url/URL/uri 等关键词时未触发系统补全字段检查（参照 trusted-sources.md 第 7 节）

**真实误报案例**:

| 案例 ID | 漏洞类型 | 误判根因 | 正确判定 |
|---------|---------|---------|----------|
| fb6af014 | FileUpload | 仅看到 deployKey 在 Deploy 接口可控，未追溯写入接口 (Create) 的校验 | safe（跨接口数据流，写入侧受限） |
| 021bc016 | SSRF | 假设 ExcelRecord.coverUrlMap 来自 JSON 用户输入，实际来源为 DB 查询 | safe（DB 查询=可信数据源） |

### Step 5.1: Map/Collection 类型值来源追踪（新增）

**触发条件**: source 类型为 Map/List/Set/数组等集合类型，或其数据流经过 `.get(key)`/`.getOrDefault()` 提取

**核心问题**: CodeQL 将 Map<String, String> 容器的声明位置标记为 source，但实际 **Map value 的来源可能完全不同于 Map 容器本身的声明入口**。FP 高发场景：
- Map 字段声明在 @RequestBody DTO 中 → Agent 误判所有 value 均为用户可控
- 实际 Map 的 value 来自 DB 查询/内部服务调用/业务映射表
- 或 Map 值为空（运行时字节无输入）

**必做动作**:

1. **Map 写入点追溯**（验证 value 的实际来源）：

   | 场景 | 验证方法 | 判定规则 |
   |------|----------|----------|
   | Map 在 Controller 层直接声明 | 检查是否有 `new HashMap<>()` + `.put()` 调用链 | `.put()` 的 value 来源决定可控性 |
   | Map 作为 DTO 字段 | grep 所有 `.put(key, value)`、`putAll()`、`Map.of()`、`Stream.collect()` 调用 | 追溯每个 value 的来源变量 |
   | Map 由 JSON 反序列化注入 | 检查字段是否被反序列化框架（Jackson/Gson）使用 | 还需验证运行时是否必有值 |
   | Map 通过 builder/setter 赋值 | grep 所有 `.setCoverUrlMap()`、`builder().coverUrlMap()` 调用处 | 检查调用方传入的 Map 来源 |
   | Map.get(key) 提取值 | 追溯该 Map 实例的**所有写入点**，确认 key 对应的 value 来源 | key 不存在 → 返回 null 数据流断裂 |

2. **Map 值来源类型确认**：

   ```
   map.put(key, value) 或 map = service.getData()
       │
       ├─ value 来自 @RequestBody/@RequestParam 等用户输入 → 用户可控
       ├─ value 来自 DB 查询（Dao/Repository/Mapper） → 可信数据源，标记不可控
       ├─ value 来自内部服务（gRPC/RPC/Feign） → 需分析调用方受控性
       ├─ value 来自 Kconf/配置中心 → 可信数据源，标记不可控
       ├─ value 来自硬编码常量（"static final" / 枚举） → 不可控，标记安全
       └─ value 来自 Map.of()/Map.copyOf() 等不可变 Map → 检查传入值来源
   ```

3. **Map 运行时值验证**（综合判定）：

   ```
   Map 字段声明在 DTO 中
       │
       ├─ Controller 层声明 + 用户直接 .put() 外部输入 → 用户可控
       ├─ DTO 字段 + 由 DB 查询填充 → 不可控（来源为 DB）
       ├─ DTO 字段 + 由内部服务填充 → 受限可控（需分析上游入口）
       ├─ DTO 字段 + 反序列化注入但非必填 → 运行时可能为空
       └─ Map.get(key) 且 key 无 containsKey 检查 → 返回 null，数据流断裂
   ```

**强制输出**（不输出此标签则不能进入 Step 6）:
```
[MAP_VALUE_ORIGIN] map变量: {变量名} | 容器来源: {Controller声明/DTO字段/内部创建} | value 写入点: {.put()/setter/反序列化/Stream} | value 来源: {用户输入/DB/内部服务/Kconf/硬编码/无法追溯} | 可控性: {用户可控/不可控/受限可控/可能为空}
```

**结束门槛**:
- value 来源为 DB/Kconf/硬编码 → 直接判定 safe，跳到 Step 6.5 输出 JSON
- value 来源为用户输入 → 进入 Step 6 继续分析
- value 来源为内部服务 → 进入 Step 6，但限制置信度
- 无法追溯写入点（未找到 .put()/setter 调用） → 标注"运行时可能为空"，进入 Step 6 但降低置信度

**禁止**:
- 看到 Map<String, String> 在 @RequestBody DTO 中就默认所有 value 用户可控
- 忽略 Map 实例的实际构造/填充位置，仅依赖 CodeQL 的 source 标记
- 未追溯 `.put()` 调用链直接判定 Map value 可控性

### Step 5.1.1: 业务语义分析（Map/Collection 类型必做）

**触发条件**: Step 5.1 执行后，source 类型为 Map/List/Set/数组等集合类型

**核心问题**: 代码层 Map 字段声明在 DTO 中即可被用户传入，但**业务层可能有系统自动补全机制，用户实际不在请求中传入该字段**。这是 SSRF 误报的高发场景——如 coverUrlMap 由视频服务补全、video_url 由 VOD 服务补全。**混淆"代码层声明"与"运行时实际来源"是 FP 的根因。**

**必做动作**:

0. **字段名预匹配**（新增入口检查）：
   - 加载 trusted-sources.md 第 7 节（常见系统补全字段列表）
   - 比对 source 字段名与系统补全字段名模式列表
   - 字段名匹配模式列表 → **自动触发"系统补全字段"判定流程**，跳过第 1 步搜索，直接执行第 2 步
   - 字段名不匹配模式列表 → 执行下方第 1 步（搜索字段在业务流程中的实际来源）

1. **搜索字段在业务流程中的实际来源**：

   | 搜索动作 | grep 命令 | 目的 |
   |----------|-----------|------|
   | 搜索字段名在项目中的引用 | `grep -rn "cover_url\|coverUrl\|videoUrl" --include="*.java"` | 了解字段被哪些类使用/赋值 |
   | 搜索字段写入点（service/补全逻辑） | `grep -rn "setCoverUrl\|put(\"cover_url\|put(coverUrl" --include="*.java"` | 查找系统侧赋值调用 |
   | 搜索字段在测试/调用处是否被传入 | `grep -rn "coverUrlMap" --include="*.java"` | 确认调用方是否传值 |
   | 搜索关键词如 VideoApiClient/PhotoInfoFacade | `grep -rn "VideoApiClient\|PhotoInfoFacade\|VideoService" --include="*.java"` | 查找系统补全服务 |

2. **识别是否为"系统补全字段"**：

   | 特征 | 判定 | 说明 |
   |------|------|------|
   | 字段由 VideoApiClient/PhotoInfoFacade 等服务端批量补全 | ✅ 系统补全字段 | 用户不在 JSON 请求中传入此字段 |
   | 字段由 VOD/ASR/CDN 等服务端填充 | ✅ 系统补全字段 | 上游服务赋值，用户不可控 |
   | 字段在业务流程中被硬编码赋值或从 DB 查询填充 | ✅ 系统补全字段 | 代码层不可控 |
   | 字段仅在响应中出现（响应 DTO），非请求入参 | ✅ 系统补全字段 | 用户无法传入 |
   | 字段无明确的系统补全服务，仅声明在 DTO 中 | ❌ 非系统补全字段 | 需继续追溯用户输入路径 |

3. **综合判定**：

   ```
   搜索字段在业务流程中的来源
       │
       ├─ 找到系统补全服务（VideoApiClient/VOD/ASR等）→ ✅ 系统补全字段
       │   └─ 历史标注"不可控/为空"直接适用，无需找到用户输入赋值语句
       │
       ├─ 字段仅在响应 DTO 中（非请求入参）→ ✅ 业务层不可传入
       │   └─ 标记 safe，运行时用户不传入
       │
       ├─ 字段由 DB 查询填充 → ✅ 数据源可信
       │   └─ 标记 safe
       │
       └─ 未找到系统补全证据，值来源为用户输入或无法追溯 → 继续 Step 5.3
   ```

**强制输出**（不输出此标签则不能进入 Step 6）:
```
[BIZ_SEMANTIC] 字段名: {字段} | 系统补全服务: {VideoApiClient/VOD/ASR/DB/无} | 是否为系统补全字段: {是/否} | 业务层限制: {有/无} | 结论: {safe/继续分析}
```

**结束门槛**:
- 确认为系统补全字段 → 直接判定 safe，跳到 Step 6.5 输出 JSON
- 非系统补全字段 → 进入 Step 5.3 继续分析

**真实误报案例**：

| 案例 ID | 漏洞类型 | 误判根因 | 正确判定 |
|---------|---------|---------|----------|
| 021bc016 | SSRF | 未执行业务语义分析，假设 coverUrlMap 来自 JSON 用户输入，实际由 VideoApiClient 服务端补全 | safe（系统补全字段，用户不传入） |

**禁止**:
- 在 Step 5.1 追溯不到 .put() 调用链时，直接假设"用户输入"
- 忽略系统补全服务的存在，仅依赖代码层 Map 声明位置判定可控性
- 系统补全字段场景下仍要求找到"明确赋值语句"才推翻用户可控假设

### Step 4.1: 代码版本一致性验证

**触发条件**: CodeQL JSON 中包含 `commitHash` 字段

**必做动作**:
1. 提取 CodeQL JSON 中的 `commitHash` 字段
2. 对比当前检出代码版本：
   ```bash
   git rev-parse HEAD
   ```
3. 判断一致性：
   - **一致** → 继续 Step 5
   - **不一致** → 执行版本切换：
     ```bash
     git checkout {commitHash}
     ```
   - **切换失败**（commit 不存在）→ 在 `remarks` 字段标注版本差异，继续使用当前版本分析

**输出格式**:
```
[VERSION_CHECK] CodeQL扫描版本: {commitHash[:8]}, 当前分析版本: {currentHash[:8]}
[VERSION_STATUS] {一致/已切换/版本缺失}
```

**结束门槛**:
- 版本一致或已成功切换 → 进入 Step 5
- 版本不一致且无法切换 → 在最终 JSON 的 `remarks` 字段标注版本差异，继续分析

**恢复步骤**（分析完成后必须执行）:
- 若执行了 `git checkout {commitHash}` 切换版本，分析完成后必须恢复：
  ```bash
  git checkout -  # 切回原分支
  ```

**禁止**:
- 忽略版本差异直接分析（会导致 FP）
- 分析完成后未切回原分支（会导致后续分析基于错误版本）

### Step 4.2: SSRF 代理接入检查（仅 SSRF/XXE/FileDownload 类漏洞）

**触发条件**: 漏洞类型为 SSRF/go_ssrf/NodeJS_SSRF/java-ssrf/xxe/file_download

**必做动作**:

对于 SSRF 相关漏洞，按漏洞类型文档（references/{lang}/{lang}-ssrf.md）中定义的隔离代理检查流程执行，并加载 references/common/ssrf-proxy.md 中的识别规则。

**输出格式**：
```
[SSRF_PROXY_CHECK] {已接入隔离代理: 变量名/配置源 | 未找到代理配置}
```

**结束门槛**:
- 已确认接入 SSRF 隔离代理 → 记录为事实防护，继续 Step 5
- 未找到代理配置 → 继续 Step 5（需在后续步骤验证代码层防护）

### Step 4.4: 参数可控性深度验证（Command Injection/RCE 类必做）

**触发条件**: 漏洞类型为 command-injection/java-rce/go-rce，且初始判断为 vulnerability

**必做动作**:

1. 追踪参数实际来源：

| 来源类型 | 识别方法 | 安全语义 |
|----------|----------|----------|
| HTTP 外部入口 | `@RequestParam`, `@PathVariable`, POST body | 外部可控 → 继续分析 |
| gRPC 内部调用 | `@KrpcMethod`, `RpcContext` | 需验证调用方身份 |
| 内部服务调用 | 同项目其他 Service 调用 | 调用方可能受控 |
| 配置文件/数据库 | `@Value`, `config.get()`, `db.query()` | 需验证写入接口权限 |

2. 验证攻击链完整性：

| 检查项 | 验证动作 | 判定规则 |
|--------|----------|----------|
| 入口可达性 | 检查接口是否有 @KrpcMethod/@RequestMapping | 无外部入口 → risk-a |
| 调用方身份 | 搜索接口被谁调用：`grep -rn "methodName(" --include="*.java"` | 仅内部调用 → 攻击面受限 |
| 认证/授权 | 检查接口是否有 @PreAuthorize, @Secured 等 | 有认证 → 攻击者需先突破认证 |

3. 分析业务语义约束：

| 检查项 | 分析内容 | 判定规则 |
|--------|----------|----------|
| 参数预期格式 | 参数在业务上应该是什么格式？ | 不符合业务语义的值无法攻击 |
| 命令上下文 | 注入的命令在实际环境是否存在？ | 命令不存在 → 攻击失败 |
| 业务价值 | 即使注入成功，能造成什么危害？ | 危害有限 → 需重新评估 |

**真实误报案例**：

| 项目 | 告警类型 | 误判根因 | 正确判定 |
|------|---------|---------|---------|
| 内部服务 | Command_Injection | 仅关注校验遗漏 `&&`，未分析：1) 接口为 gRPC 内部调用；2) loginCommand 预期格式为 `kml login`；3) `login && whoami` 中 `login` 非有效命令 | safe |

**输出格式**：
```
[CONTROLLABILITY] {参数名} | 来源: {外部/内部服务/配置} | 调用方: {受控/不受控} | 业务语义: {符合/不符合} | 攻击路径: {完整/受限/不存在} | 结论: {可控/不可控}
```

**结束门槛**:
- 参数来源为内部服务/配置，且调用方受控 → 判定为 risk-a 或 safe
- 参数业务语义与恶意值不匹配 → 判定为 safe
- 其他情况 → 继续 Step 5

**禁止**：
- 仅分析代码校验逻辑，不验证参数实际来源
- 假设参数完全可控，不分析业务语义约束

### Step 5: 历史运营经验查询

**触发条件**: JSON 中包含 git_address 字段（**本步骤不可跳过，无论查询结果如何都必须执行**）

**必做动作**:
1. 从输入 JSON 提取以下字段：

   | JSON 字段 | 脚本参数 | 说明 |
   |-----------|----------|------|
   | `git_address` | `--git_address` | Git 仓库地址 |
   | `raw_vul_type` | `--raw_vul_type` | 原始漏洞类型（如 `java-ssrf`、`NodeJS_SSRF`） |
   | `source_file` | `--file_path` | source 点文件路径 |

2. 执行历史查询脚本：
   ```bash
   python3 $REDTRACE_SKILLS_DIR/route-skills/upstream/skills/code-audit/scripts/history_query.py \
     --git_address "{git_address}" \
     --raw_vul_type "{raw_vul_type}" \
     --file_path "{source_file}"
   ```

   > **注意**：`--file_path` 对应 JSON 中的 `source_file` 字段，**不是** `file_path`。

3. 解析脚本输出的 JSON 结果，记录查询结果

**结果使用**（辩证使用原则）:
- 历史记录仅作为研判参考，**不替代代码验证**
- 必须重新验证历史记录中提到的防护措施是否仍然存在
- 优先参考"精确匹配"的记录，其次参考"项目级匹配"
- **历史全标 safe 时的处理策略**：
  1. **独立验证必须执行**：即使历史 10 条全标 safe，仍需独立验证当前告警的数据流和防护措施是否仍然存在
  2. **防护存在性验证**：确认历史记录中提到的防护措施在当前代码中仍然存在（如白名单检查函数未被删除）
  3. **防护类型判断**：区分"拦截型"（失败即 return/raise）与"净化型"（返回安全值），拦截型防护只需确认存在即可
  4. **不得过度质疑防护完整性**：当历史全 safe 且当前代码确认存在拦截型防护时，直接判定 safe，无需审查"防护不完整"
  5. **历史记录数量阈值**：当历史全标 safe 且记录超过 3 条时，应更采信历史结论，重点验证历史依据是否仍然有效
  6. **历史备注优先级规则（强制执行）**：
     | 历史备注类型 | 处理策略 | 是否审查完整性 |
     |-------------|---------|--------------|
     | "参数有进行过滤" | 确认存在拦截型校验（return/throw）→ 直接判定 safe | **禁止审查完整性** |
     | "已接入xxx代理" | 确认代理配置存在 → 直接判定 safe | 禁止审查完整性 |
     | "文件名不可控" | 确认硬编码限制存在 → 直接判定 safe | 禁止审查完整性 |
     | "路径已校验" | 确认 normalize + startsWith 存在 → 直接判定 safe | 禁止审查完整性 |
     | "内部服务调用" | 确认接口调用方受控 → 判定 safe/risk-a | 需验证调用方 |
     | "防护不完整" | 必须审查防护完整性 | 必须审查 |
  7. **快速判定门禁（历史全safe时）**：当满足以下**所有**条件时，**立即判定 safe，跳过 Step 6.4 反方审查**：
     - 历史记录全为 safe（≥2条）
     - 历史备注包含"参数有进行过滤"或其他明确防护描述
     - 当前代码中存在拦截型校验（失败即 return/throw）
     - 历史备注未标注"防护不完整"或"存在绕过"
  8. **禁止行为（强制执行）**：
     - **禁止**：对"参数有进行过滤"的历史记录，质疑防护可绕过性（如认为黑名单不完整）
     - **禁止**：对历史备注明确标注的防护进行"完整性"深度审查
     - **必须**：历史备注为"参数有进行过滤"且代码存在拦截型校验时，直接判定 safe
     - **例外**：仅当历史备注明确提到"防护不完整"或"存在绕过案例"时，才可审查防护完整性
  9. **历史备注精确解读**：
     - "参数有进行过滤" = 存在某种校验机制，非完整黑名单也可接受
     - 重点验证：校验是否为拦截型（失败即中断），而非校验是否完整
  9. **例外情况**：仅当历史记录备注明确提到"防护不完整"或存在已知绕过案例时，才需审查防护完整性
- **历史记录备注解读规范（与优先级规则对照）**：
  | 历史记录表述 | 技术含义 | 处理方式 | 是否审查完整性 |
  |-------------|---------|---------|--------------|
  | "参数有进行过滤" | 存在拦截型校验机制 | 确认拦截型校验存在 → 直接判定 safe | **禁止** |
  | "已接入xxx代理" | SSRF 隔离代理已配置 | 确认代理配置存在 → 直接判定 safe | **禁止** |
  | "文件名不可控" | 硬编码文件名/扩展名 | 确认硬编码限制 → 直接判定 safe | **禁止** |
  | "路径已校验" | normalize + startsWith 验证 | 确认路径校验存在 → 直接判定 safe | **禁止** |
  | "参数可控性受限" | 参数来源非完全外部可控 | 需验证参数实际来源 | 需验证 |
  | "内部服务调用" | gRPC 接口调用方受控 | 需验证调用方身份 → 可能为 risk-a | 需验证 |
  | "业务语义限制" | 恶意值不符合业务预期格式 | 需分析业务约束 | 需验证 |
  | "防护不完整" | 历史已知防护有缺陷 | 必须审查防护完整性 | **必须** |
  | "存在绕过案例" | 历史有成功绕过记录 | 必须审查防护完整性 | **必须** |
- **历史漏洞记录的处理**：当历史存在漏洞记录时，需确认当前版本是否已修复，而非直接判定为漏洞
- **时间衰减验证**：历史记录超过 6 个月时，需额外验证代码是否已变更（`git log --since="6 months ago" -- {相关文件}` 检查最近修改），代码已变更的历史记录参考价值降低
- **历史标注关键词权重提升**：当历史记录备注/标注包含以下关键词时，提高研判阈值，需要更强证据才能推翻：
  | 关键词 | 含义 | 处理策略 |
  |--------|------|---------|
  | "不可控" / "域名不可控" / "参数不可控" | 历史判定数据源不可控 | **除非找到明确的外部用户赋值语句（如 @RequestBody 字段、@RequestParam 等），否则维持"不可控"判断**。<br>**注意**：代码层类型声明（DTO 字段）不等于运行时实际来源。字段声明在 JSON 反序列化 DTO 中不代表用户一定传入该字段。 |
  | "不可达" / "路径不可达" | 历史判定数据流不可达 | 需找到赋值语句 + 控制流路径同时存在，才能推翻 |
  | "为空" / "未使用" / "输入字节为空" | 历史判定运行时实际值为空 | 验证当前运行时路径是否仍有值（检查上游是否赋值），仅凭代码类型声明不能推翻。<br>**核心原则**：代码层声明不等于运行时实际来源。Map 字段在 DTO 中声明不等于用户在 JSON 请求中一定传入该 Map。Map 可能由系统服务端补全或运行时为空。 |
  | "安全" / "无风险" / "标记误报" | 历史判定为误报 | 需综合验证 scope + 代码变更 + 防护变化，三项中至少两项一致才能推翻 |
  | "业务层限制" / "系统补全字段" | 历史判定有业务约束/字段由系统服务补全 | 1）确认系统补全服务（VideoApiClient/VOD/ASR等）是否仍存在<br>2）**无需找到用户输入赋值语句**，系统补全字段直接视为运行时不可控<br>3）系统补全字段场景下，历史标注"不可控/为空" **直接适用**，无需也不应要求"明确赋值语句"才推翻 |
  **规则**：人工标注含"不可控"/"不可达"/"为空"/"未使用"时，除非找到**明确赋值语句**（代码层面的变量赋值、必填注解、或确认前端必然传递），否则**维持原判断**。仅凭代码层面的类型声明/参数定义不能推翻人工标注。<br>
  **例外规则（系统补全字段）**：当字段被识别为系统补全字段（由 VideoApiClient/VOD/ASR/DB 等服务端赋值，或字段名匹配 trusted-sources.md 第 7 节系统补全字段列表）时，历史标注"不可控/为空"**直接适用**，无需追溯用户输入赋值语句。系统补全 = 用户不传入 = 运行时不可控。此例外规则优先级高于上述通用规则。<br>
  **推导逻辑**：对于系统补全字段场景，判定链路为：<br>
  1）字段在代码层声明（DTO/Model）→ 代码层"可传入"<br>
  2）但系统补全服务（如 VideoApiClient）在业务流程中覆盖该字段 → 运行时实际值不由用户提供<br>
  3）历史标注"不可控/为空"基于业务层认知 → 直接适用<br>
  4）结论：safe。无需找到用户输入赋值语句来推翻，因为系统补全服务的存在已说明用户不传入。
  **强制输出**（当检测到关键词时）：
  ```
  [ANNOTATION_WEIGHT] 关键词: {不可控/不可达/为空/安全/系统补全字段} | 推翻证据: {有/无/不适用(系统补全)} | 证据类型: {赋值语句/必填注解/系统补全服务/不适用(系统补全)} | 结论: {维持原判/推翻}
  ```
- **强制输出**（历史全 safe 时）：
  ```
  [HISTORY_VALIDATION] 历史记录: {内容摘要} | 当前验证: {防护存在/已变更} | 结论采纳: {是/否}
  ```

### Step 5.3: 运行时值验证（新增）

**触发条件**: Step 5 完成历史查询，source 被判定为外部输入（HTTP/gRPC 入口）

**核心问题**: CodeQL 数据流分析仅证明"代码层面参数可传递到 sink"，但未验证"运行时实际是否有值"。FP 高发场景：source 字段在运行时实际为空、固定值或业务层限制了输入值。

**必做动作**:

1. **字段实际来源确认**（区分代码层可控性与运行时实际值）：

   | 场景 | 验证方法 | 判定规则 |
   |------|----------|----------|
   | @RequestBody JSON 字段，非必填 | 检查是否有 `@NotNull`/`@NotEmpty`/`required=true`/业务层判空 | 无必填校验且前端不传 → 实际值为空/默认值 |
   | @RequestParam 可选参数 | 检查 `required=true`/`defaultValue` | required=false 且未传 → 实际为空 |
   | 内部服务间 DTO 字段 | 追溯调用方是否传入该字段（grep 调用处） | 调用方未赋值 → 实际为空 |
   | 经 JSON 反序列化的字段 | 检查字段是否有 `@JsonProperty` 或是否被序列化 | 上游未传该字段 → 反序列化后为 null/默认值 |

1.1. **系统补全字段验证**（当 source 来自 @RequestBody/@RequestParam 时强制）：

   0. **字段名预匹配**（新增入口检查）：
      - 加载 trusted-sources.md 第 7 节（常见系统补全字段列表）
      - 比对 source 字段名与系统补全字段名模式列表
      - 字段名匹配列表 → 直接触发系统补全判定，无需搜索即可确认"字段可能由系统补全"
      - 字段名不匹配列表 → 执行下方常规搜索流程

   | 验证动作 | grep 命令 | 判定规则 |
   |----------|-----------|----------|
   | 搜索字段名在业务流程中的来源 | `grep -rn "字段名\|fieldName\|field_name" --include="*.java"` | 找到系统补全服务 → 运行时用户不传入 |
   | 搜索调用方是否传入该字段 | `grep -rn "set字段名\|setFieldName\|json字段名" --include="*.java"` | 调用方未赋值 → 实际为空 |
   | 搜索字段在请求/响应 DTO 中的角色 | 检查 DTO 定义，区分响应字段 vs 请求字段 | 响应 DTO 字段 → 用户无法传入 |

   **判定**：找到系统补全服务（VideoApiClient/VOD/ASR/DB等），或字段仅在响应 DTO 中，或字段名匹配 trusted-sources.md 第 7 节系统补全字段列表 → **业务层限制，运行时用户不传入** → 直接判定 safe

1.2. **置信度降级规则**（Map/Collection 类型且历史标注"不可控/为空"时强制）：

   当 source 为 Map/List/Set/数组类型，且历史标注包含"不可控"/"为空"/"输入字节为空"时：

   | 场景 | 处理方法 |
   |------|----------|
   | 字段名匹配 trusted-sources.md 第 7 节系统补全字段列表 | 直接引用历史标注，置信度设为"中"，标注"业务层限制" |
   | 字段名不匹配列表，但历史标注明确含"不可控/为空" | 即使代码层 DTO 声明了该字段，运行时值可能为空。置信度降一级（高/中/低） |
   | 字段为 Map 类型 + 代码层声明在 DTO + 无业务层写入证据 | 运行时实际可能为空（上游不传该字段），置信度不可设为"高" |

   **核心原则**：Map 字段在 DTO 中声明不等于用户在 JSON 请求中传入该 Map 且非空。运行时值的不确定性应体现为置信度降级而非直接否定历史标注。

2. **业务语义约束验证**（验证"即使可控，实际攻击价值"）：

   | 检查项 | 验证动作 | 判定规则 |
   |--------|----------|----------|
   | 预期值格式 | 字段在业务上的预期值格式（URL/ID/名称/路径等） | 非预期格式的值会被业务层拒绝 |
   | 字段长度限制 | 检查是否有 `@Size`/`@Length`/业务层长度校验 | 超长值被截断/拒绝 |
   | 枚举/字典映射 | 检查字段值是否经过枚举转换或字典映射 | 非白名单值被映射为默认值/null |
   | 前端限制 | 字段在前端是否有下拉框/单选等限制 | 但注意前端限制可绕过，不作为主要依据 |

3. **防御性检查流程**：

   ```
   确认 source 为外部输入（@RequestBody/@RequestParam等）
       │
       ├─ 检查是否为系统补全字段（Step 5.1.1 已执行）
       │   ├─ 是系统补全字段 → ✅ safe，运行时用户不传入
       │   └─ 非系统补全字段 → 继续检查
       │
       ├─ 检查字段是否有必填约束（@NotNull/required=true）
       │   ├─ 有必填约束 → 继续分析（运行时必有值）
       │   └─ 无必填约束 → 确认前端/调用方是否必然传递
       │       ├─ 前端必然传递 → 继续分析
       │       └─ 不一定传递 → 标注"运行时值可能为空"
       │
       ├─ 检查字段是否有默认值（defaultValue/字段默认值）
       │   ├─ 默认值为安全值（空字符串/false/0）→ 攻击面降低
       │   └─ 默认值无安全意义 → 继续分析
       │
       ├─ 检查字段的业务语义约束
       │   ├─ 有枚举/字典映射 → 值受限 → 验证映射后是否仍危险
       │   └─ 无业务语义约束 → 继续分析
       │
       └─ 综合判定
           ├─ 运行时值不可控（无必填 + 未传递 + 默认值安全）→ 攻击面降低，标注低置信度
           └─ 运行时值可控（有必填或必然传递）→ 进入 Step 6
   ```

4. **数据流变换路径验证**（当数据流经过变换时，验证返回值是否为空）：

   | 变换类型 | 验证方法 | 判定规则 |
   |---------|----------|----------|
   | `Map.get(key)` | ① 检查调用方是否确保 key 存在于 Map 中（containsKey 检查/必然存在的键）<br>② **追溯 Map 实例的 value 来源**（参照 Step 5.1 执行） | 未确保 key 存在 → 返回 null，数据流断裂<br>value 来自 DB/内部服务 → 不可控，标记 safe |
   | `Optional.ofNullable().orElse()` | 检查 orElse 默认值是否为空/安全 | 默认值为空 → 下游仍可能为 null |
   | `Optional.orElseGet()` | 检查 orElseGet 的 supplier 是否返回值 | 返回 null → 下游仍为 null |
   | `Optional.map()` 链式调用 | 检查 map 中是否有 null 检查 | 无 null 检查 → 可能为 null |
   | 三元表达式 `condition ? a : b` | 验证两分支是否均为非空 | 任一分支为空 → 运行时可能为 null |
   | `stream().filter().findFirst().orElse()` | 验证 filter 是否命中 + orElse 默认值 | filter 未命中 + 默认值为 null → 数据流断裂 |

   **规则**: 如果变换后值为 null/empty，且后续代码无非空赋值或校验，则数据流断裂，标记为 safe

   **强制输出**（当检测到数据流变换路径时）：
   ```
   [TRANSFORM_CHECK] 变换类型: {Map.get/Optional/三元/stream} | 返回值: {可能为空/非空} | value来源: {用户可控/DB/内部服务/硬编码/无法追溯} | 后续赋值: {有/无} | 数据流断裂: {是/否}
   ```

**强制输出**：
```
[RUNTIME_VALIDATION] source: {变量名} | 必填约束: {有/无} | 默认值: {安全/无/不适用} | 业务语义约束: {有/无} | 系统补全字段: {是/否} | 运行时值判定: {可控/可能为空/受限/系统补全-安全}
```

**结束门槛**:
- 运行时值判定为"可能为空"或"受限"且无其他攻击路径 → 判定 safe，跳到 Step 6.5 输出 JSON
- 系统补全字段 → 判定 safe，跳到 Step 6.5 输出 JSON
- 运行时值可控 → 进入 Step 6

**真实误报案例**：

| 案例 ID | 漏洞类型 | 误判根因 | 正确判定 |
|---------|---------|---------|----------|
| 021bc016 | SSRF | 假设 coverUrlMap 来自 @RequestBody JSON 用户输入，实际运行时该字段输入字节为空，域名不可控 | safe（运行时实际无输入） |

**禁止**:
- 仅根据代码层寄存器/参数声明判定"用户可控"，未验证运行时实际值
- 忽略 @RequestParam required=false 场景下的空值可能性
- 忽略 Map.get()/Optional/三元表达式等变换后返回值为 null 的可能性
- 未追溯 Map 实例的 value 实际来源（.put() 调用链/DB查询/内部服务），仅凭 Map 容器声明判定 value 可控性
- **未搜索字段在业务流程中的实际来源，忽略系统补全字段导致误判为用户可控**

### Step 6: 研判与结论

**触发条件**: Step 4-5 完成证据收集

> Step 6 包含 5 个子步骤（6.1-6.5），必须按顺序执行。
> 子步骤 6.2 为控制流可达性门禁，子步骤 6.3-6.4 构成"初步判断 + 反方审查"机制。

#### Step 6.1: 按流程执行分析

执行漏洞类型文档定义的分析流程，**不在此处输出结论**，将分析证据传递给后续子步骤。

**必做动作**:
1. 按照对应漏洞类型的"研判流程 SOP"逐步执行
2. 使用 Grep/Glob/Read 获取上下文信息
3. 执行对应漏洞类型的黄金法则强制执行顺序
4. 对每个可疑点执行双重验证
5. 按照对应漏洞类型的 Checklist 逐一检查
6. 对照"防护措施"表格判定防护强度
7. 若涉及防护措施，执行防护完整性验证（强制检查清单）
8. 发现自定义校验函数（如 `validate_safe_file_path`、`validatePath`、`checkSql` 等）时，**必须读取函数实现**，判断是拦截型还是净化型，再结合调用处控制流判定安全性；禁止仅凭函数名或调用位置下结论
9. **跨语言边界分析**：当发现代码执行外部脚本/命令时，必须分析下游脚本内容
10. **业务语义校验**（Command Injection/RCE 类必做）：当防护措施看似不完整时，分析业务语义约束

**业务语义校验规则**：

| 检查项 | 分析内容 | 判定规则 |
|--------|----------|----------|
| 参数预期格式 | 参数在业务上应该是什么格式？ | 不符合业务语义的值难以攻击 |
| 命令上下文 | 注入的命令在实际环境是否存在？ | 命令不存在 → 攻击失败 |
| 业务价值 | 即使注入成功，能造成什么危害？ | 危害有限 → 需重新评估 |
| 调用场景 | 接口是外部暴露还是内部调用？ | 内部调用 → 攻击面受限 |

**真实误报案例**：

| 项目 | 告警类型 | 误判根因 | 正确判定 |
|------|---------|---------|---------|
| 内部服务 | Command_Injection | 仅关注校验遗漏 `&&`，未分析业务语义：1) 预期格式为 `kml login`；2) `login && whoami` 中 `login` 非有效命令；3) 接口为内部 gRPC 调用 | safe |

**输出格式**：
```
[SEMANTIC_CHECK] 参数预期格式: {格式} | 恶意值语义: {有效/无效} | 业务价值: {高/低} | 调用场景: {外部/内部} | 结论: {需继续分析/攻击价值有限}
```

**结束门槛**：
- 恶意值不符合业务语义 → 判定为 safe
- 接口为内部调用且调用方受控 → 判定为 risk-a
- 其他情况 → 继续分析

**跨语言边界分析规则**：

当发现以下模式时，必须分析下游脚本内容：

| 上游语言 | 触发模式 | 必做动作 |
|----------|----------|----------|
| Go | `exec.Command("python"/"bash"/"sh", "-c", ...)` | 读取并分析脚本 |
| Java | `ProcessBuilder` / `Runtime.exec()` | 读取并分析脚本 |
| Python | `subprocess.run(["go"/"node", ...])` | 读取并分析脚本 |
| JavaScript | `child_process.exec/spawn(...)` | 读取并分析脚本 |

分析流程：
1. 提取脚本文件路径或内联脚本内容
2. 使用 Read 工具读取脚本文件
3. 分析脚本中是否存在：eval/exec 执行用户数据、模板注入（如 Jinja2 `{{user_input}}`）、命令拼接（如 `os.system("cmd " + user_input)`）
4. 如存在上述风险点，判定为 vulnerability

输出格式：`[CROSS_LANG] {上游语言} → {下游语言} | {脚本路径} | {脚本风险点} | {结论}`

**禁止**:
- 在完成 Step 6.2 控制流可达性验证之前输出任何结论

**强制证据输出**（进入 Step 6.2 之前必须逐项输出）:

```
[EVIDENCE]
1. source 变量: {变量名}, 类型: {类型}, 可控性: {用户可控/不可控/间接可控}
2. sink 调用: {方法名}, 行号: {行号}, sink 语义: {执行型/生成型}
3. 数据流路径: {source → 中间节点 → sink 的完整链路}
4. 防护措施: {有/无}, 类型: {拦截型/净化型/无}, 函数名: {xxx}
5. 已检索文件列表: {列出所有 Read/Grep 过的文件和行号}
6. 控制流分析: {拦截型/净化型/无校验}, 拦截方式: {return/throw/exit/无}
```

缺少任何一项 → 进入 Step 6.2 前必须补充检索。

**结束门槛**:
- 分析完成，[EVIDENCE] 6 项全部有值 → 进入 Step 6.1.1
- 关键代码缺失，无分析基础 → 直接判定 unknown 输出 JSON（此时无分析基础，跳过 6.1.1-6.5）

#### Step 6.1.1: 硬编码安全数据检查（路径遍历/文件上传必做）

[CONSTANT_DATA_CHECK]
检查 sink 点的最终参数是否包含硬编码安全数据。当用户可控变量与硬编码常量拼接时，硬编码部分可能限制了暴露面。

**执行方式**：加载对应的漏洞类型文档（references/{lang}/{lang}-path-traversal.md 或 {lang}-file-upload.md），按其中定义的硬编码安全数据判定规则执行。

**输出格式**：
```
[CONSTANT_DATA_CHECK] {变量名} | 硬编码部分: {.json/.txt/...} | 用户可控部分: {前缀/不可控} | 判定: safe/需继续分析
```

**结束门槛**:
- sink 参数满足漏洞文档中的硬编码安全判定规则 → 直接判定 safe，跳到 Step 6.5 输出 JSON
- sink 参数不满足 → 继续 Step 6.2

#### Step 6.2: 控制流可达性验证

**source → sink 的数据流能否实际到达？** 检查变量传递链中是否存在控制流中断，被污染数据根本无法到达 sink。

**必做动作**:

检查 source 到 sink 之间是否存在以下控制流中断：

| 中断类型 | 识别方法 | 判定影响 |
|----------|----------|----------|
| return/raise/exit | 校验函数失败后 return → 后续 sink 不可达 | 只有通过校验的数据到达 sink → 安全 |
| if 条件分支 | 条件不满足时跳过 sink → 部分路径不可达 | 需分析条件是否可被绕过 |
| 异常处理 | try 块中校验失败 throw → catch 中未调用 sink | sink 不可达 → 安全 |
| 循环 break/continue | 循环内条件 break → 跳过后续 sink | 需分析循环条件 |
| 白名单校验中断 | `whitelist.contains(x)` 失败后 throw/return → 后续 sink 不可达 | 仅白名单内值可到达 sink → 安全 |
| 自定义安全检查器 | `SSRFChecker.checkAndBlock` / `isAllowedFileUrl` / `hasForbidStr` / `isZipFile` 等自定义函数内部有 throw/return | 需读取函数实现确认阻断 → 若确认阻断则安全 |
| **查询型校验** | **调用 store.get(key) 或类似查询操作 → 查询失败时后续代码不执行** | **key 不存在 = 隐式 return → sink 不可达 → 安全** |
| **文件系统隐式阻断** | **路径遍历类：硬编码文件名/扩展名限制、Files.exists 前置校验** | **无效路径/固定文件名 → 无法攻击 → 安全** |

**文件系统隐式阻断识别规则（路径遍历类必做）**：

| 模式 | 代码示例 | 安全语义 |
|------|----------|----------|
| 硬编码文件名 | `path.resolve("content.lines.txt")` | 攻击者只能读取特定名称文件 |
| 硬编码扩展名 | `path + ".json"` | 限制文件扩展名，无法读取敏感文件 |
| 文件存在性检查 | `if (!Files.exists(path)) return;` | 路径不存在 = 隐式阻断，后续 sink 不执行 |
| 目录创建失败 | `Files.createDirectories(dir)` 抛异常 | 无效路径无法创建，sink 不可达 |

**真实误报案例**：

| 项目 | 告警类型 | 误判根因 | 正确判定 |
|------|---------|---------|---------|
| outlines | Absolute_Path_Traversal | 仅关注 fileId 可控，未识别 `resolve(CONTENT_LINES_TXT)` 硬编码文件名限制 | safe |
| ksfloan-risk-admin | Command_Injection | 历史 2 条 safe 记录备注"参数有进行过滤"，但仍质疑防护完整性（黑名单可绕过），未正确应用快速判定门禁 | safe |

输出格式：`[CONTROL_FLOW] {source} → {sink} | 隐式阻断: 硬编码文件名限制 | 结论: 不可达`

**查询型校验识别规则**：

| 模式 | 代码示例 | 安全语义 |
|------|----------|----------|
| Map/List 查询 + null 检查 | `obj = store.get(key); if (obj == null) return;` | key 不存在 → 直接 return → 后续 sink 不执行 |
| 数据库查询 + 空结果检查 | `record = db.query(id); if (record == null) throw;` | 记录不存在 → 抛异常 → 后续 sink 不执行 |
| 缓存查询 + 缺失检查 | `val = cache.get(key); if (val == null) return;` | 缓存未命中 → 直接 return → 后续 sink 不执行 |
| Optional 包装 + 空值处理 | `Optional.ofNullable(obj).orElseThrow()` | 值不存在 → 抛异常 → 后续 sink 不执行 |

**查询型校验的安全判定流程**：
```
发现查询型校验（如 store.get(key)）
    │
    ├─ 检查查询键来源
    │   ├─ 用户可控（如 @PathVariable）→ 继续分析
    │   └─ 系统生成（如 UUID、数据库查询）→ 直接判定 safe（不可预测）
    │
    ├─ 检查查询失败时的控制流
    │   ├─ 有显式 return/throw → sink 不可达 → safe
    │   ├─ 无显式 return，但后续代码依赖查询结果（如 obj.method()）→ NPE 风险 → 需继续分析
    │   └─ 无 null 检查，直接使用 → 可能 NPE → 需继续分析
    │
    └─ 综合判定
        ├─ 查询键不可预测 + 查询失败阻断控制流 → safe
        └─ 查询键可预测 或 控制流未阻断 → 继续分析 sink 可达性
```

**关键区分**：
- **拦截型校验**（校验失败即 return/raise）：能到达 sink 的数据已通过校验，sink 使用原始变量还是返回值不影响安全性
- **净化型校验**（返回安全值但不断流）：sink 必须使用校验后的返回值，使用原始变量仍为漏洞

**强制输出**（不输出此标签则不能进入 Step 6.3）:
```
[CONTROL_FLOW] {source} → {sink} | 中断类型: {拦截型return/拦截型throw/查询型/净化型/无中断} | 结论: {可达/不可达}
```

**结束门槛**:
- 数据流可到达 sink（无控制流中断，或中断可绕过）→ 进入 Step 6.2.5
- 数据流不可达 sink（拦截型校验阻断，或用户输入仅用于选择 client/dataSource 未参与 SQL/路径构建）→ 直接判定 safe 输出 JSON

#### Step 6.2.5: 历史全 safe 快速判定门禁

**触发条件**: 满足以下所有条件
1. 历史记录全为 safe
2. 代码中存在拦截型校验（return/throw）
3. 历史备注提到的防护在代码中仍存在

**必做动作**:
1. 确认历史记录数量：精确匹配 + 项目级匹配 safe 记录总数
2. 确认历史备注类型：是否为"参数有进行过滤"等明确标注防护的备注
3. 确认代码中拦截型校验仍然存在：grep 确认校验函数未被删除
4. 确认校验为拦截型：失败时 return/throw，而非返回安全值

**快速判定规则**：

| 条件组合 | 判定 | 后续动作 |
|---------|------|---------|
| 历史全 safe + 备注"参数有进行过滤" + 存在拦截型校验 | safe | **跳过 Step 6.3-6.4，直接进入 Step 6.5 输出 JSON** |
| 历史全 safe + 备注"已接入xxx代理" + 代理配置存在 | safe | 跳过 Step 6.3-6.4，直接进入 Step 6.5 |
| 历史全 safe + 其他类型备注 + 存在拦截型校验 | safe | 进入 Step 6.3，但 6.4 不审查防护完整性 |
| 历史存在漏洞记录 | 需分析 | 正常进入 Step 6.3-6.4 |

**强制输出**：
```
[HISTORY_GATE] 历史safe记录: {数量} | 备注: {内容} | 拦截型校验: {存在/不存在} | 判定: {快速safe/继续分析}
```

**禁止行为**：
- 满足快速判定条件时仍调用 subagent 审查防护完整性
- 质疑黑名单可绕过、正则不完整等技术细节
- 忽略历史备注的明确结论

**结束门槛**：
- 满足快速判定条件 → 判定 safe，跳过 Step 6.3-6.4，进入 Step 6.5 输出 JSON
- 不满足快速判定条件 → 进入 Step 6.3

#### Step 6.3: 初始结论与推理

基于 Step 6.1-6.2 的分析结果，形成初始结论并输出完整推理链。

**必做动作**:
1. 形成初始结论：从 vulnerability / safe / unknown 中选择
2. 输出结构化推理链：

```
[初步判断] {vulnerability/safe/unknown}

[推理步骤]
1. 漏洞本质判断：{描述漏洞是否存在，引用黄金法则}
2. 数据流追踪：{从 source 到 sink 的完整路径，包含关键代码行号}
3. 控制流可达性：{source→sink 之间有无 return/raise/break 等控制流中断，被污染数据能否实际到达 sink}
4. 防护分析：{发现哪些防护，是否有效，是否完整}
5. 入口可达性：{是否有 HTTP/gRPC 入口，如何确认}
6. 关键判定证据：{支撑结论成立/不成立的决定性代码事实，与数据流路径互补}

[置信度] {高/中/低}
[置信度理由] {为什么是这个置信度}
```

**置信度降级规则**：

| 场景 | 降级规则 |
|------|----------|
| source 为 Map/List/Set/数组类型 + 历史标注含"不可控"/"为空"/"输入字节为空" | 置信度降一级（高/中/低），理由中注明"运行时值不确定性" |
| source 为 Map/List/Set/数组类型 + 字段名匹配 trusted-sources.md 第 7 节系统补全字段列表 | 即使代码层可控，置信度设为"中"，标注"业务层限制" |
| source 为 DTO/Model 字段（非 @RequestParam 直接入参） | 置信度不可设为"高"，需在理由中注明来源追溯结果 |
| source 经跨接口数据流（接口 A 写入 DB → 接口 B 读取） | 置信度降一级，理由中注明"跨接口间接污染" |
| 历史标注含"业务层限制" + 当前仍存在系统补全服务 | 直接判定 safe，置信度"中"，理由中注明"业务层限制适用" |

**核心原则**：代码层声明不等于运行时实际来源。置信度应体现运行时值的不确定性，而非仅基于代码层数据流分析。

**结束门槛**:
- 推理链完整，每个步骤有明确证据 → 进入 Step 6.3.1

#### Step 6.3.1: 历史记录适用范围校验（新增）

**触发条件**: Step 6.3 已形成初始结论，且历史记录查询结果不为空

**核心问题**: Agent 引用历史记录时，未校验历史判断的适用范围是否与当前告警一致。FP 高发场景：历史记录针对的是不同字段、不同调用路径或不同数据流起点，但 Agent 错误引用或错误排除历史结论。另一个 FP 高发场景：历史备注包含"域名不可控/不可达"等约束关键词，但 Agent 直接标记为"不适用"后判定 vulnerability，未追溯 Map 值实际来源（参照 Step 5.1）。

**必做动作**:

校验历史记录与当前告警的一致性，所有检查项必须逐项执行：

| 检查项 | 验证方法 | 匹配规则 |
|--------|----------|----------|
| **字段一致性** | 历史记录中的 source 文件/字段与当前告警的 source 文件/字段是否相同 | 不同字段 → 历史不适用，标记为"不适用" |
| **调用路径一致性** | 历史记录中的 sink 文件/方法与当前告警的 sink 文件/方法是否相同 | 不同调用路径 → 历史不适用 |
| **数据流起点一致性** | 数据流入口（HTTP 入口/内部调用/DB/Kconf）是否相同 | 不同起点 → 历史不适用 |
| **防护措施一致性** | 历史记录提到的防护措施在当前代码中是否仍然存在 | 防护已变更/删除 → 历史不适用 |
| **代码版本一致性** | 自历史记录以来相关代码是否发生过变更 | `git log -- {相关文件}` 有变更 → 需重新验证 |
| **历史标注关键词一致性** | 历史备注是否包含"不可控"/"不可达"/"为空"/"未使用"等关键词，如包含则需交叉验证 Step 5 标注权重规则 | 存在关键词且当前未找到明确赋值语句 → 维持原判，标记为"需标注权重验证" |
| **历史约束条件验证**（新增） | 历史备注包含"不可控/不可达/为空/未使用"等约束关键词，**且当前初始判断为 vulnerability** | ① 追溯 source 字段值的实际来源（Map 类型参照 Step 5.1 执行）<br>② 验证历史约束在当前代码中是否已被突破<br>③ 通过 `.put()`/`.set()`/写入点调用链确认值来源 | 未找到明确用户输入写入点 → 维持历史约束结论，标记为"需价值源验证" |

**适用范围判定矩阵**：

| 条件组合 | 判定 | 后续动作 |
|---------|------|----------|
| 字段、路径、起点全部一致 + 防护仍然存在 + 标注关键词无冲突 | 适用 | 采用历史结论，直接进入 Step 6.3.1.1 |
| 字段或起点不一致 | **不适用** | 标记"不适用历史判断"，进入 Step 6.4 |
| 字段、路径一致但防护已变更 | **部分适用** | 参考历史判定但重新分析当前防护，进入 Step 6.4 |
| 代码版本有变更 | **需重新验证** | 进入 Step 6.4 |
| 标注含"不可控/不可达/为空/未使用"关键词且未找到明确赋值语句 | **需标注权重验证** | 参考 Step 5 标注权重规则，进入 Step 6.4 |
| 标注含"不可控/不可达"关键词 + 当前初始判断为 vulnerability + source 为 Map/Collection 类型 | **需价值源验证** | 按 Step 5.1 追溯 value 实际来源：<br>• 来自 DB/内部服务/Kconf → 维持历史 safe 结论，进入 Step 6.3.1.1<br>• 来自用户输入 → 历史约束已被突破，进入 Step 6.4 |

**强制输出**：
```
[HISTORY_SCOPE_CHECK] 历史记录ID: {案例ID/摘要} | 字段一致性: {一致/不一致} | 调用路径一致性: {一致/不一致} | 数据流起点一致性: {一致/不一致} | 防护措施一致性: {存在/已变更} | 标注关键词: {无/含不可控/含不可达/含为空/含未使用} | 约束验证: {已执行/不适用} | 价值源追溯: {用户输入/DB/内部服务/Kconf/不适用} | 适用范围判定: {适用/不适用/部分适用/需重新验证/需标注权重验证/需价值源验证}
```

**禁止**:
- 历史备注含"不可控/不可达/为空/未使用"关键词时，直接标记为"不适用"而不追溯 value 实际来源
- 仅凭 CodeQL 的 source 标记（Map 容器声明位置）否定历史约束条件
- 看到 Map<String, String> 在 @RequestBody 中就认为"历史判断依据与当前代码不一致"

#### Step 6.3.1.1: 历史结论快速采纳门禁（新增）

**触发条件**: Step 6.3.1 判定历史记录"适用"

**必做动作**:

确认以下条件全部满足时，直接采纳历史结论：

| 条件 | 验证方式 |
|------|----------|
| 历史记录判定为 safe | 检查历史 conclusion_type |
| 历史备注有明确防护描述 | 检查备注字段（参数有进行过滤/已接入代理等） |
| 当前代码中防护仍然存在 | grep 确认校验函数未被删除 |
| 防护为拦截型 | 失败时 return/throw |

**强制输出**：
```
[HISTORY_ADOPT] 历史结论: {safe/vulnerability} | 防护存在: {是/否} | 拦截型: {是/否} | 采纳判定: {采纳/不采纳}
```

**结束门槛**:
- 推理链完整，每个步骤有明确证据 → 进入 Step 6.4

#### Step 6.4: 反方视角审查

从相反角度挑战 Step 6.3 的初始结论，主动寻找推翻证据。

**根据初始结论方向，执行对应的反方审查**：

**情形 A：初始 vulnerability → 搜索"为什么可能不是漏洞"**

按以下固定顺序检查，前 3 项为必做：

| 优先级 | 审查维度 | 具体动作 |
|--------|----------|----------|
| 1（必做） | 遗漏的防护 | 搜索拦截器/过滤器/AOP 切面等未发现的防护，**包括白名单校验（contains+throw/return）和自定义安全检查函数（SSRFChecker/isAllowedFileUrl/hasForbidStr 等）** |
| 2（必做） | 数据流中断 | 验证数据流是否连续，中间有无拦截型校验（return/raise）导致只有安全数据到达 sink |
| 3（必做） | 可信数据源/硬编码数据 | 追踪 source 变量实际来源，是否来自配置/数据库/枚举；检查 sink 参数是否有硬编码安全后缀/前缀 |
| 4 | 框架隐式防护 | 检查框架默认防护行为 |
| 5 | 环境限制 | 检查是否非线上环境或内网隔离 |

**情形 B：初始 safe → 搜索"为什么可能是漏洞"**

按以下固定顺序检查，前 3 项为必做：

| 优先级 | 审查维度 | 具体动作 |
|--------|----------|----------|
| 1（必做） | 防护绕过 | 对照漏洞文档"常见误判场景"逐一检查，**并执行以下子检查** |
| 2（必做） | 防护不完整 | 验证防护是否覆盖所有路径，**并执行以下子检查** |
| 3（必做） | 数据流分支遗漏 | 检查 catch/finally 块和异步调用中的未分析分支 |
| 4 | 间接可控 | 检查上游数据写入路径，source 是否间接可控 |
| 5 | 编码/解码链 | 检查 URLDecoder/decode/unescape 等多重编码 |

**维度 1（防护绕过）逐项子检查**：

| 检查项 | 验证动作 | 判定规则 |
|--------|----------|----------|
| 正则锚定 | 检查正则是否有 ^ 和 $ | 未锚定 = 存在绕过风险 |
| 编码变体 | 检查是否处理 URL 编码/双重编码 | 未处理 = 可绕过 |
| 大小写绕过 | 检查匹配是否 case-insensitive | 不区分大小写 = 可能绕过 |
| 已知绕过手法 | 对照漏洞文档"常见误判场景"逐一检查 | 存在绕过 = 非有效防护 |

输出格式：`[VALIDATION_CHECK] {检查项} | {结果: 通过/未通过} | {风险描述}`

**维度 2（防护不完整）逐项子检查**：

| 检查项 | 验证动作 | 判定规则 |
|--------|----------|----------|
| 白名单完整性 | 列出所有已知安全域名/值，检查是否遗漏 | 缺少必要值 = 不完整 |
| 路径覆盖 | 检查所有入口路径是否都经过校验 | 有路径绕过校验 = 不完整 |
| 重定向链 | 检查是否存在 follow redirect 导致绕过 | 未禁止重定向 = 可能绕过 |
| DNS Rebinding | 检查域名校验后是否重新解析 | 解析可变 = 可能绕过 |

输出格式：`[VALIDATION_CHECK] {检查项} | {结果: 通过/未通过} | {风险描述}`

**情形 C：初始 unknown → 验证"是否能进一步确认"**

| 审查维度 | 具体动作 |
|----------|----------|
| 替代检索路径 | 尝试不同检索策略获取缺失代码 |
| 推断合理性 | 基于已有证据推断最可能结论，标注低置信度 |

**强制要求**：
- **情形 A（初始 vulnerability）**：按固定顺序覆盖前 3 个维度（遗漏的防护、数据流中断、可信数据源）
- **情形 B（初始 safe）**：按固定顺序覆盖前 3 个维度（防护绕过、防护不完整、数据流分支遗漏），同时区分历史记录情况：
  - **历史全 safe（Step 6.3.1 已判定适用）**：前 3 维度必做，但不得过度质疑已确认的有效防护，需确认代码未变更导致新增 sink 或数据流路径变化
  - **历史全 safe（已跳过 Step 6.3.1 快速采纳门禁）**：直接跳过 Step 6.4
  - **历史有漏洞 或 无历史记录**：前 3 维度必做
  - **历史记录明确标注防护不完整**：第 2 维度（防护不完整）必须深入执行
- **情形 C（初始 unknown）**：全部覆盖
- 每个维度有具体检索/验证动作，非形式化审查
- 仅做一轮，不迭代
- 反方审查只能产出两种结果：推翻（附具体证据，引用推理步骤编号 1-6）或 维持
- 禁止将初始结论改为"倾向有效"、"可能有效"等非标准值

**结束门槛**:
- 情形 A/B：至少完成 3 个审查维度 → 进入 Step 6.5
- 情形 C：完成全部维度 → 进入 Step 6.5

#### Step 6.5: 最终结论输出

综合 Step 6.3 初始结论和 Step 6.4 审查结果，形成最终结论。

**必做动作**:
1. 如审查导致结论变更，在 `judgment_rationale` 中记录变更理由
2. 如审查未改变结论，在 `judgment_summary` 中记录"已执行反方审查，结论维持"
3. 根据审查结果调整置信度
4. 按照"输出规范"章节输出纯 JSON 格式结论

**结论变更规则**:

| 初始结论 | 审查发现 | 最终结论 |
|----------|----------|----------|
| vulnerability | 发现遗漏的有效防护 | safe |
| vulnerability | 发现数据流中断 | safe 或 unknown |
| vulnerability | 未发现推翻因素 | 维持 vulnerability |
| safe | 发现防护可绕过 | vulnerability |
| safe | 发现防护不完整 | vulnerability |
| safe | 未发现推翻因素 | 维持 safe |
| unknown | 获取到关键证据 | vulnerability 或 safe |
| unknown | 仍无法确认 | 维持 unknown |

**禁止（适用于 Step 6 全部子步骤）**:
- 仅凭历史记录判定（必须读取实际代码）
- 跳过防护措施检查
- 跳过误报排除检查
- 跳过控制流可达性验证（Step 6.2）
- 跳过历史记录适用范围校验（Step 6.3.1）
- 跳过反方视角审查（Step 6.4）
- 在 Step 6.1-6.4 输出最终 JSON（最终输出仅在 Step 6.5）

### Step 7: 结案业务核查（新增）

**触发条件**: Step 6.5 已形成最终结论（vulnerability）

**核心问题**: 代码层面的数据流分析判定为漏洞，但特定业务场景下可能存在不可见的业务层限制。FP 高发场景：KIM Webhook、内部服务间调用、定时任务、**系统补全字段**等——这些场景的消息/数据来源在代码层面看似"用户可控"，但业务层实际有限制。**业务层限制应作为独立判定维度，而非仅作为 vulnerability 后的补充核查。**

**必做动作**:

1. **业务场景识别**：判断当前接口是否属于以下特殊业务场景：

   | 业务场景 | 特征 | 需确认事项 |
   |----------|------|-----------|
   | Webhook/回调 | 接口由外部平台调用（KIM/飞书/钉钉等），URL 参数来自平台消息 | 消息附件 URL 实际由谁提供？平台是否限制？ |
   | 内部服务调用 | gRPC 接口，无 HTTP 暴露 | 调用方是否受控？是否有认证？ |
   | 定时任务/Scheduler | 由定时器触发，无外部请求入口 | 数据来源是否为配置/DB？ |
   | 消息队列消费 | MQ 消费者消费消息触发 | 消息生产方是否受控？是否有消息校验？ |
   | 管理后台操作 | 仅管理员可操作的接口 | 是否有权限控制？操作审计？ |
   | **系统补全字段** | source 字段在程序代码中声明于 DTO/Model，但运行时值由系统服务端补全 | 字段名是否匹配 trusted-sources.md 第 7 节系统补全字段列表？是否由 VideoApiClient/VOD/ASR 等服务赋值？ |

2. **业务层限制验证**：

   | 业务场景 | 验证方法 | 判定规则 |
   |----------|----------|----------|
   | KIM 消息附件 | 确认 KIM 消息附件的 URL 是否由平台生成/限制 | 平台生成 → 不可控 |
   | 内部 gRPC 调用 | 确认调用方身份（grep 调用处） | 服务端受控 → 攻击面受限 |
   | 定时任务 | 确认数据源（配置中心/DB） | 不可控来源 → safe |
   | MQ 消费 | 确认消息生产方是否有权限控制 | 生产方不可信 → 继续分析 |

3. **强制输出**（结论为 vulnerability 时必须输出）：
   ```
   [BIZ_CHECK] 业务场景: {Webhook/内部服务/定时任务/MQ/管理后台/不适用} | 业务层限制: {有/无} | 业务层限制说明: {具体限制} | 结论: {不受影响/攻击面受限/不适用}
   ```

**结束门槛**:
- 确认存在业务层限制 → 降级为 safe 或 risk-a，更新最终结论
- 无业务层限制 → 维持原结论

**真实误报案例**：

| 案例 ID | 漏洞类型 | 误判根因 | 正确判定 |
|---------|---------|---------|----------|
| bd944e48 | SSRF | 仅分析代码数据流（KIM Webhook URL 从消息解析 → new URL().openConnection()），未确认业务层限制——KIM 消息附件 URL 为平台生成，用户不可控 | safe（业务层限制） |

**禁止**:
- 对非特殊业务场景的告警，形式化执行本步骤
- 发现业务层限制后仍坚持 vulnerability 结论

## 快速判定

> **静态分析的边界**：静态分析报告代码风险，不报告运行时可验证性。
> **网络不可达 = 事实防护**：无 HTTP 入口本身就是一种防护。本模式不输出 risk-a，网络不可达场景归入 safe 或 unknown。
