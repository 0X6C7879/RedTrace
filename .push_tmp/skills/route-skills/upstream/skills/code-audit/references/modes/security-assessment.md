# Security Assessment 模式 - 安全评估报告生成

从外部未授权用户视角出发，基于白盒分析结果与代码审计，发现可被外部人员（普通用户，非管理员/非白名单用户）验证的真实风险路径。核心产出：经代码验证的完整风险链路。

---

## 核心原则

> **视角**: 外部未授权用户视角。测试角色为已注册的普通用户（非管理员、非白名单用户），通过正常 HTTP 接口实施未授权访问。
>
> **白盒结果仅供参考**: 白盒分析从单个接口维度出发，缺乏全局思维。其标记的漏洞/风险**不一定真实存在**。本模式需以全局视角重新审视，验证漏洞的真实可验证性，过滤误报，发现白盒未识别的组合风险路径。
>
> **风险链路是完整链路**: 每条风险链路必须是一个从未授权用户起点到最终危害的完整可复现路径。对于越权类漏洞，必须分析越权目标 ID 的获取方式（从哪个接口泄露、是否可遍历、是否可预测）。
>
> **信息不完整也记录**: 即使链路中存在信息缺失（如无法确认 ID 获取路径、无法确认某步是否可达），也应记入报告，但必须明确标注缺失条件和完成验证还需什么。

---

## 与其他模式的区别

| 维度 | api-audit / mr-review | security-assessment |
|------|----------------------|---------------------|
| 视角 | 单接口代码安全分析 | 外部未授权用户全局风险路径 |
| 输入 | 代码 diff 或 API 路径 | DB 白盒结果 + 仓库代码 |
| 输出 | 单接口的 JSON findings | 跨接口完整风险链路报告 |
| 全局性 | 单接口维度，无跨接口关联 | 全局视角，跨接口组合，过滤误报 |

## CLI 工具

### 安全评估查询 CLI

从 DB 查询白盒审计结果，作为报告生成的数据输入：

```bash
python3 $REDTRACE_SKILLS_DIR/route-skills/upstream/skills/code-audit/scripts/security_assessment_query_cli.py <command> --git <git_address> --output-file <path>
```

| 命令 | 说明 | 关键参数 |
|------|------|----------|
| `vulns` | 全部漏洞/风险扁平列表（解析 result_json） | `--git`, `--severity`, `--conclusion`, `--output-file`（推荐） |
| `apis` | 带审计结果的 API 完整记录 | `--git`, `--audit-status`, `--output-file`（推荐） |
| `by-module` | 按 file_path 分组（漏洞密度分析） | `--git`, `--audit-status`, `--output-file` |
| `apis-by-file` | 按文件分组返回所有接口（含 PASS），跨接口组合分析数据基础 | `--git`, `--audit-status`, `--output-file` |
| `params` | 跨 API 共享参数（链路推理基础） | `--git`, `--output-file` |
| `stats` | 仓库统计概览 | `--git`, `--output-file` |

> **所有查询推荐使用 `--output-file`**：结果保存到文件，避免 bash 输出解析问题。

## 执行流程

```
安全评估报告生成
├── Step 0: 输入解析 → git_address + 仓库路径
├── Step 1: 数据收集 → CLI 查询 DB 白盒结果 + 读代码理解项目
├── Step 2: 白盒结果过滤 → 以全局视角过滤误报和不可验证项
├── Step 3: 风险链路构造 → 构造完整可验证链路（含 ID 获取路径）
└── Step 4: 输出报告
```

### Step 0: 输入解析与验证

**输入**：

| 字段 | 必需 | 说明 |
|------|------|------|
| `git_address` | 是 | 仓库 Git 地址 |
| 仓库路径 | 是 | 当前工作目录，用于读取代码验证链路 |

**必做动作**：
1. 运行 `stats` 命令验证 DB 中有该 git_address 的审计结果
2. 若 `block_count + warning_count == 0`，提示先运行 api-audit 模式完成白盒审计

**结束门槛**：有审计数据 → 进入 Step 1

---

### Step 1: 数据收集与项目理解

同时获取 DB 白盒数据与项目代码，建立全局认知。

**CLI 查询**（全部使用 `--output-file`）：
1. `vulns` → 白盒漏洞/风险列表
2. `apis` → 带审计结果的 API 详情
3. `by-module` → 按模块分组
4. `params` → 跨 API 共享参数
5. `stats` → 仓库统计
6. `apis-by-file` → 同文件接口分组（含 PASS 接口），建立同文件接口全景

**代码理解**（与 CLI 查询并行）：
1. **项目结构**：目录结构、pom.xml/package.json，识别技术栈和模块划分
2. **认证模型**：Grep 搜索鉴权中间件/拦截器，识别哪些接口需要认证、哪些公开、哪些需要管理员权限
3. **数据流向**：识别用户标识（userId/accountId）在接口间的传递方式，哪些接口返回其他用户的 ID
4. **架构预分析上下文**（若 .redtrace/code-audit/PROJECT_CONTEXT.md 存在）：
   1. 读取 .redtrace/code-audit/PROJECT_CONTEXT.md 中以下标记的条目：
      - `RPC-DOWNSTREAM:` — 已知有下游认证的端点（身份凭证+资源ID同时传递）
      - `ID-TYPE:` — 资源标识符可枚举性分类
      - `PUBLIC-DATA:` — 已公开数据端点
      - `TENANT-BOUNDARY:` — 租户边界信息
      - `STRIDE-{S,T,R,I,D,E}:` — 威胁模型标签（用于风险链路优先级排序，参见 `references/common/threat-consumption.md`）
   2. 在后续白盒结果过滤（Step 2）和风险链路构造（Step 3）中，这些条目作为**先验参考线索**使用（消费纪律见 SKILL.md「.redtrace/code-audit/PROJECT_CONTEXT.md 消费纪律」，不得据此跳过代码确认）
   3. **STRIDE 消费**：命中 `STRIDE-I`(信息泄露) / `STRIDE-E`(权限提升) 的端点，优先构造风险链路

---

### Step 2: 白盒结果过滤

白盒分析结果中存在大量误报和不可验证项。在构造风险链路之前，必须以全局视角过滤。

**过滤规则**：

| 过滤类型 | 判断方法 | 示例 |
|---------|---------|------|
| 接口不可达 | 读代码确认该路由在认证模型下对外部用户不可达 | 仅限内网/管理后台的接口，外部用户无法访问 |
| 有全局防护 | 读代码确认存在全局中间件/拦截器的有效防护 | 全局权限校验拦截器已覆盖该路由 |
| 参数不可控 | 读代码确认越权参数来自服务端注入而非用户输入 | `userId` 从 JWT token 中提取，非请求参数 |
| 白盒误判 | 读代码确认白盒结论与代码实际逻辑不符 | 白盒标记"无权限校验"，但实际有 `@PreAuthorize` 注解 |
| 低危害无链路价值 | 单独漏洞危害极低且无法与其他漏洞组合 | 布尔值越权（仅返回 true/false）、公开数据查询 |
| 架构预分析已知安全模式 | 读取 .redtrace/code-audit/PROJECT_CONTEXT.md 中 RPC-DOWNSTREAM / PUBLIC-DATA 记录，与白盒 finding 比对 | 白盒标记 IDOR，但 .redtrace/code-audit/PROJECT_CONTEXT.md 记录该端点传递了身份凭证给下游 RPC |

**必做动作**：
1. 对每条白盒 finding，Read 对应的 Controller/Handler 代码
2. 按上述规则逐一判定是否保留
3. 记录保留原因和过滤原因
4. **架构上下文比对**：对每条白盒 finding，检查 .redtrace/code-audit/PROJECT_CONTEXT.md 中是否有匹配的已知安全模式
   - 端点匹配 `RPC-DOWNSTREAM:` 且记录了身份凭证传递 → 过滤（不用于构造风险链路）
   - 端点匹配 `PUBLIC-DATA:` → 过滤（公开数据无风险价值）
   - 资源标识符匹配 `ID-TYPE:` 且标记为不可枚举 → 标记验证难度为\"高\"
   - 资源匹配 `TENANT-BOUNDARY:` 且为同租户横向 → 过滤

**禁止**：
- 不读代码就保留白盒结论
- 不读代码就过滤白盒结论

---

### Step 3: 风险链路构造

基于 Step 2 过滤后的真实漏洞，构造完整风险链路。每条链路必须回答：**外部用户如何从零开始，经过哪些步骤，达成什么危害。**

#### 3.1 风险链路类型

| 链类型 | 描述 | 关键验证点 |
|--------|------|-----------| 
| 单漏洞多步骤验证 | 一个漏洞需要多个步骤才能完成验证 | 每个步骤的必要条件和衔接关系 |
| 多漏洞组合验证 | 多个漏洞组合形成新的风险能力 | 漏洞 A 的产出是否可作为漏洞 B 的输入 |
| 越权链 | 越权目标 ID 的获取 → 越权操作 | ID 从哪个接口获取、是否可遍历、是否可预测 |

#### 3.2 越权 ID 获取路径分析（强制）

对于所有越权类漏洞（IDOR / BrokenAccessControl），必须分析越权目标 ID 的获取方式：

| 获取方式 | 判断方法 | 可验证性 |
|---------|---------|---------| 
| 列表接口泄露 | Read 列表接口代码，确认返回包含目标 ID | 高 — 直接获取 |
| 搜索接口泄露 | Read 搜索接口代码，确认可通过关键词搜到目标 ID | 高 — 可枚举 |
| ID 可预测 | Read ID 生成逻辑，判断是否为自增/时间戳/短随机数 | 高 — 可遍历 |
| ID 为 UUID | Read ID 生成逻辑，确认为标准 UUID v4 | 低 — 需要其他泄露途径 |
| ID 为 BlobStore key / Bucket name / AES 加密参数 | 查阅 .redtrace/code-audit/PROJECT_CONTEXT.md ID-TYPE 记录，确认为不可枚举 | 极低 — 需要其他泄露途径 |
| 其他接口返回 | Read 其他接口的响应结构，逐字段检查是否包含目标 ID | 中 — 取决于接口可达性 |
| 无获取途径 | 所有接口都不返回目标 ID，且 ID 不可预测 | 不可验证 — 降级或丢弃 |

**验证流程**：
1. 确定越权目标参数名（如 `orderId`、`userId`）
2. 搜索所有接口的代码，检查哪些接口的返回值包含该参数
3. 判断外部用户是否可以访问这些接口
4. 判断参数值是否可遍历（自增 ID）或可预测

#### 3.3 链路验证（强制）

对每条候选链路，**必须通过 Read 工具逐步验证**：

1. **起点验证**：确认测试角色作为普通用户可以到达链路的第一个接口
2. **每步验证**：确认上一步的产出确实是下一步所需的输入
3. **终点验证**：确认最终操作确实能达成描述的危害
4. **防护验证**：Grep 搜索中间是否有全局拦截/校验逻辑阻断链路
5. **下游认证验证**：确认越权端点是否在 .redtrace/code-audit/PROJECT_CONTEXT.md 中被标记为有下游认证
   - .redtrace/code-audit/PROJECT_CONTEXT.md 有 `RPC-DOWNSTREAM:` 记录 → 丢弃或标记为"待确认，存在下游认证"
   - 无记录 → 维持

**判定**：
- 全部验证通过 → 记入报告为 **已确认风险链路**
- 部分步骤无法确认（缺少信息）→ 记入报告为 **待确认风险链路**，标注缺失条件
- 已确认不可达（有代码证据证明阻断）→ 丢弃该链路

**禁止**：
- 不读代码就将链路记入报告
- 假设某接口返回特定字段
- 假设参数值可获取而不验证获取路径

#### 3.4: 跨接口组合分析（强制）

单接口审计以"接口"为粒度，无法发现"每个接口单独判定安全、但组合后存在逻辑缺陷"的风险。本步骤以同文件接口为分析单元，识别跨接口的组合风险。典型场景：接口 A（查询/列表，PASS）泄露资源 ID，接口 B（操作，PASS）以该 ID 为入参但无归属校验——单看 A、B 都合理安全，组合后构成越权链。

**触发条件**：`apis-by-file` 结果中，同文件下存在 ≥2 个已审计接口（含 PASS），且存在数据/操作耦合的可疑组合（不要求"有漏洞"——纯 PASS 组合也触发）。

**主 agent 职责**（调度与验收，不做深度分析）：
1. 从 `apis-by-file` 结果识别可疑文件组：同文件 ≥2 接口，且语义上存在"查询/列表/详情"与"修改/删除/撤销"的成对关系（用 `api_description` / `functional_impact` 预筛）
2. 按文件切片，每个可疑文件派一个子代理（同一文件不拆分，保证上下文完整）
3. 并行启动子代理，每个完成后验收
4. 汇总子代理返回的风险结论，纳入报告"待确认风险链路"章节

**组合模式识别**：

> 模式 1、2 适用于所有组合（含纯 PASS）；模式 3（共享校验方法）需同文件内至少存在 1 个非 PASS 接口作为缺陷传染源，纯 PASS 组合不适用。

| 组合模式 | 识别方法 | 风险判定 |
|---------|---------|---------|
| 查看 + 操作 | 同文件存在"查询/列表/详情"语义接口 + "修改/删除/撤销"语义接口 | 读操作类接口的归属校验逻辑，若缺失或可被查询类接口的返回值绕过 → 纳入风险链路 |
| 信息泄露 + 越权 | 同文件存在返回资源 ID 的接口 + 以该资源 ID 为入参的接口 | 资源 ID 可枚举且操作接口无归属校验 → 构造组合链路（ID 传播靠子代理 Read 代码确认，不假设返回字段） |
| 共享校验方法 | 读取有漏洞接口的防护描述 + PASS 接口的 `passed_checks` 描述，匹配是否调用同一校验方法 | 若同一校验方法已被确认有缺陷，PASS 接口同样受影响。判定"共享"须满足代码同构的全部 4 项条件（相同方法体 / 相同调用链结构 / 相同参数来源 / 相同业务权限校验，见 api-audit 模式「代码同构判定清单」），避免误判表层方法名相同但实际逻辑不同的场景 |

**子代理 prompt 模板**：

```
使用 code-audit 技能对以下文件做跨接口组合安全分析。

注意：
- 不要把临时文件放在 `/tmp/` 下，临时文件统一放在当前项目路径的 `.code-audit-tmp/` 下，没有该目录就创建一个。
- 严禁执行 `rm -rf`、`sqlite3`、`drop`、`delete`等不可逆命令！！
- 代码分析工具选择：见 SKILL.md「工具使用规范」章节

项目信息：
- Git 地址：{git_address}
- 仓库路径：{repo_path}

分析目标文件：{file_path}

该文件接口全景（含 PASS 接口）：
{api_summary_json}

分析要求：
1. Read 该文件全部接口源码
2. 识别三类组合模式：查看+操作、信息泄露+越权、共享校验方法
3. 判定"共享校验方法"时，须满足代码同构的全部 4 项条件（相同 Handler 方法体 / 相同 Service/DAO 调用链结构下沉到同一 sink / 相同参数来源 / 相同业务权限校验），不得简化判定，详见 api-audit 模式「代码同构判定清单」
4. 对每个可疑组合，验证是否存在跨接口风险（ID 传播靠读代码确认，不假设返回字段）
5. 每个判定的风险必须有代码依据（file_path:line_number）

输出 JSON：
{"file_path": "...",
 "combinations_analyzed": [...],
 "risks": [{"risk_type": "查看+操作/信息泄露+越权/共享校验方法",
            "involved_apis": ["api_path1","api_path2"],
            "code_evidence": [{"file": "...","line": N,"desc": "..."}],
            "severity": "high/medium/low",
            "description": "风险描述（含为何单接口安全但组合后有缺陷）"}]}
```

**验收与容错**：
- 子代理输出 JSON 解析失败或格式不符 → 重试 1 次
- 连续 2 个文件组的子代理失败 → 熔断，该文件组由主 agent 自行分析（降级，不中断流程）
- 风险结论必须含 `code_evidence`，无代码依据的丢弃（与 3.3"禁止不读代码就写入报告"一致）
- 主 agent 对子代理返回的 risk 抽样 ≥1 条，Read 其 `code_evidence` 指向的行号确认依据属实后再纳入报告

### Step 4: 输出报告

输出 Markdown 格式的安全评估报告。

**报告结构**：

```markdown
# 安全评估报告 - {project_name}

**仓库地址**: {git_address}
**未授权用户视角**: 外部普通用户（已注册，非管理员）

## 1. 项目上下文

### 1.1 业务与架构
- 业务类型 / 技术栈 / 核心模块
- 认证模型（哪些接口公开 / 需登录 / 需管理员）
- 用户角色划分（普通用户 / 管理员 / 其他）

### 1.2 暴露面分析
- 外部用户可达的接口范围
- 用户间可交互的数据范围
- 关键数据类型（资金/PII/业务数据）

## 2. 已确认风险链路

> 按**危害等级降序 → 验证难度升序**排列。危害高的排前，同危害时验证门槛低的排前。

### CHAIN-{id}: {一句话描述链路危害}

**测试角色**: 普通用户
**危害等级**: {critical/high/medium}
**验证难度**: {低/中/高}
**危害描述**: {具体描述验证达成后的实际影响}

**验证步骤**:

| 步骤 | 操作 | 接口 | 目的 |
|------|------|------|------| 
| 1 | {如：登录普通用户获取 token} | POST /api/auth/login | 获取认证凭据 |
| 2 | {如：调用列表接口获取目标用户 userId} | GET /api/users/list | 获取越权目标 ID |
| 3 | {如：使用目标 userId 访问其订单数据} | GET /api/users/{userId}/orders | 越权访问他人数据 |

**越权 ID 获取路径**（越权类漏洞必填）:
- 目标参数: {userId}
- 获取方式: {列表接口泄露 / 可遍历 / 可预测 / ...}
- 获取接口: GET /api/users/list — 返回值中包含所有用户的 userId 字段
- 可遍历性: {自增ID可遍历 / UUID不可遍历 / ...}
```
