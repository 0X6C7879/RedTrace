# 审计反模式与诚实结论

本文档定义应避免的审计反模式（让审计结论失效的思维错误）与诚实结论/正面模式的输出要求。各模式适用范围见下方「适用范围区分」。

> **质量门禁引用**：SKILL.md「通用质量门禁」要求对照本文件自检，确认未触犯任一反模式。与「反幻觉约束」互补——反幻觉约束管"必须验证"，本文件管"如何判定与如何报告"。

---

## 一、审计反模式（让审计变无用的错误）

这些是让审计报告失去价值的典型错误。触犯任一条都会导致结论不可信或不可用。

> **适用范围区分**：
> - **发现型模式**（api-audit/mr-review/arch-scan/security-assessment）：产出新发现，全部反模式适用。
> - **复核型模式**（report-review）：不产出新发现只复核既有 finding，反模式 3/4/7（凑数/无证据就报/忽略业务逻辑）主要约束"不得凭空引入新发现或无依据改判"；反模式 1/5/6（档位混淆/忽略防护/信任模型）同样适用。
> - **sast-audit 例外**：sast-audit 仅输出 vulnerability/safe/unknown，不输出 risk-a/risk-b。反模式 1（档位混淆）对 sast-audit 退化为"不得把 unknown 当 vulnerability 报"。
> - **arch-scan 例外**：arch-scan 产出架构识别而非漏洞 finding，反模式 3/4/8（凑数/无证据就报/构造 exploit）不适用；反模式 6（信任模型）适用——不得把设计内信任边界当缺陷记录到 .redtrace/code-audit/PROJECT_CONTEXT.md。

| # | 反模式 | 为什么是错的 | 正确做法 |
|---|--------|-------------|----------|
| 1 | **把 risk-a/risk-b 当 vulnerability 报** | 静态有危险写法 ≠ 运行时可利用。risk-a 是网络不可达的事实防护，risk-b 是有弱防护但入口可达，二者都不是漏洞。混淆档位会让修复方误判优先级 | 严格按 SKILL.md 判定标准表归档：无 HTTP 入口→risk-a；弱防护→risk-b；无防护且可达→vulnerability。**sast-audit 例外**：仅输出 vulnerability/safe/unknown，不使用 risk 档位 |
| 2 | **把所有偏离 OWASP/框架最佳实践的都当 finding** | OWASP 是清单不是 bug 列表。每个真实业务都在做取舍：CDN 层限流是合法架构、管理端全信任是设计选择。把"建议加一道"当漏洞会淹没真问题 | 偏离最佳实践 → 归入硬化建议（hardening note），单独列出，不抬高 severity。缺一道防护而前一道已挡住攻击 = 加固而非漏洞 |
| 3 | **用 LOW 凑数让报告显得详尽** | 十个 LOW 不如三个 MEDIUM。LOW 凑数稀释修复方注意力，让真问题被忽略，并降低对报告整体信任度 | 只报有真实影响的发现。宁可出一份短而准的报告，也不出一份长而水的报告。三个 MEDIUM > 十个 LOW |
| 4 | **"potential/theoretical" 没有证据就报** | 需要用"可能""理论上""潜在"措辞时，说明还没研究透。这类发现要么后续证实为漏洞，要么是误报 | 要么给出具体攻击场景（谁、做什么、得到什么），要么不报。需要"可能"的发现 = 还需继续追代码 |
| 5 | **忽略防护措施的实际效果** | 白名单有 default 值、类型转换、参数化查询、RPC 下游传凭据——这些防护常被原报告一笔带过"无校验"。不验证 default 是固定安全值就报漏洞，是典型误报 | Read 防护实现：白名单 default 是否固定安全值？类型转换后是否仍可注入？RPC 是否同时传身份凭据？参考 false-positive-filtering.md FP-3.7/3.8/3.9 与 sanitization.md |
| 6 | **把设计内的信任模型当 bug** | 信任模型是设计前提，不是审计对象。设计说 admin 全权可信，则 admin-does-admin-things 不是漏洞。审计 trust model 是否被绕过，而不是审计 trust model 本身 | 先理解信任模型（谁可信、能做什么、哪段代码强制执行）。发现信任边界被绕过才是漏洞，发现"信任边界本身存在"不是 |
| 7 | **忽略业务逻辑与创意攻击，只查标准漏洞类** | SQLi/XSS/SSRF 是每个扫描器都查的。人工审计的价值在找扫描器找不到的：状态机违规、链式攻击、隐式信任假设、并发竞态、功能滥用 | 对每个主要工作流追问：能否跳步/回退/重放？两个请求同时发生会怎样？两个解析器对同一输入判定是否一致？功能被非预期使用会怎样？ |
| 8 | **基于解析器/运行时直觉构造 exploit** | "解析器会把它解释成…"——最逼真的误报来自未经验证的运行时假设。直觉不等于事实 | exploit 依赖解析器/运行时行为时，引用规范或实测验证。不靠直觉推理 URL 解析、模板渲染、序列化反序列化的行为 |

> **与「反幻觉约束」的分工**：反幻觉约束（SKILL.md）是硬性"必须 Read/必须追数据流/必须确认防护"的工具纪律；本文件是判定与报告层面的思维纪律。两者叠加：既不假设代码存在，也不假设可利用。

## 二、诚实结论

| 规则 | 说明 |
|------|------|
| **诚实的"无发现"是有效结论** | push hard 后（追完数据流、验证完防护、查完攻击类）仍无真实可利用发现，应明确输出"无漏洞"。不要为了"有产出"而降级凑数。诚实空结论比虚假满载更可信 |
| **"nothing found" 前必须 push hard** | 不得在浅查后即下"无发现"结论。push hard = 追完入口到 sink 的数据流、验证完所有防护实现、覆盖了该模式要求的攻击类与误报排除规则 |
| **无法读关键代码时保守维持** | 关键代码缺失/不可访问时，不得判 safe，保守维持原判定或标 unknown。参考 report-review Step 2.2.2 |

## 三、正面模式（报告校准信任）

**为什么写正面模式**：只列漏洞的报告会让读者怀疑"是不是没认真查"。明确指出代码做得好的地方，校准读者对本次审计深度的信任，也让修复方知道哪些地方不用动。

**适用模式**：security-assessment（Markdown 报告）默认包含正面模式章节；api-audit/mr-review/report-review 在 `summary.key_findings` 或 `description` 中可选简述正面模式。

| 正面模式类型 | 示例表述 |
|-------------|---------|
| 认证体系完整 | "全局拦截器覆盖所有 REST 入口，无遗漏的免认证端点" |
| 数据层防护到位 | "Repository 层统一通过 lambdaQuery.eq(userId) 隐式过滤，越权面已收敛" |
| 输入净化有效 | "所有 SQL 查询使用参数化绑定，未发现拼接路径" |
| 信任边界清晰 | "admin 操作均有 @PreAuthorize 注解，权限模型与设计一致" |

## 四、硬化建议（与 finding 严格分离）

| 规则 | 说明 |
|------|------|
| **硬化建议 ≠ finding** | 缺少第二道防护而第一道已挡住攻击 = 加固建议，不是漏洞。归入独立"硬化建议"区域 |
| **不抬高 severity** | 硬化建议的 severity 固定为 info/low，不得因"建议加防护"而把 finding 升级 |
| **单独列出** | 硬化建议不混入 vulnerabilities/risks 数组，在 summary 或报告末尾单独区块列出 |

> 参考 false-positive-filtering.md：缺限流/分页/日志等属 FP-1.x/FP-2.x，应排除出漏洞列表，转作硬化建议。
