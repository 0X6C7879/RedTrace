# 敏感信息泄露案例集

> 整合内部真实漏洞与业界经典案例，提供实战指导

## 一、内部真实案例

### 案例1：Git 仓库（.svn 目录）对外暴露泄露源代码
**系统**: 某内部系统（172.29.81.85:9000）

**漏洞描述**:
SVN 元数据目录（.svn）被部署到 Web 根目录，外部攻击者可利用该隐藏目录提取敏感信息。SVN 元数据目录本用于开发阶段追踪代码变更，当代码被发布到生产服务器时，应以导出（export）形式部署而非直接使用工作副本（working copy），否则 .svn 目录将被一并发布。

**技术细节**:
- .svn 目录包含完整的版本历史记录、文件列表、提交注释等
- 攻击者可通过 /.svn/entries 获取所有文件路径，逐一下载源代码
- 源代码中可能包含数据库连接字符串、API 密钥、内网地址等敏感配置
- SVN 导出 vs 工作副本：使用 `svn export` 而非 `svn checkout` 部署可避免此问题

**修复方案**:
从生产系统删除 .svn/.git 等版本控制目录；Web 服务器配置限制对隐藏目录（以 . 开头）的访问（如 Nginx 的 `location ~ /\. { deny all; }`）。

**经验总结**:
API 接口返回的数据需按最小权限原则过滤，不应将整个数据库对象序列化返回；生产部署必须使用 export 模式，CI/CD 流水线中需检测 .svn/.git 目录是否被包含在部署包中。

### 案例2：某内部系统敏感信息日志打印（KIM SDK 凭证泄露）
**系统**: 某内部系统（kauishou-kim）

**漏洞描述**:
kim-encryption-sdk 的一代签名拦截器/过滤器和二代签名拦截器中，存在打印 x-auth-token 等敏感凭据信息到日志的逻辑。虽然 SDK 1.0.22 版本已通过开关禁用此打印，但各 kim 服务端尚未更新到最新版本，导致修复未生效，日志中仍可能包含明文认证凭证。

**技术细节**:
- x-auth-token 属于高敏感认证凭证，泄露后攻击者可直接冒充合法用户
- 日志往往有较长的保留周期，且通常不加密存储，攻击面宽
- SDK 版本滞后导致安全修复无法及时生效，反映了依赖管理的安全风险
- 日志系统（如 ELK）如果存在未授权访问，可被批量提取凭证

**修复方案**:
日志打印内容中去除敏感信息；各 kim 服务端更新到 kim-encryption-sdk 1.0.22+ 版本并重新编译部署；建立日志敏感信息扫描机制，定期检查是否有凭证类信息写入日志。

**经验总结**:
错误信息不应暴露堆栈跟踪、SQL 语句、内部路径等敏感调试信息；日志框架（如 log4j、logback）应配置敏感字段脱敏过滤器，在框架层面统一拦截。

### 案例3：Gitlab accessToken 泄露——可直接拉取任意仓库代码
**系统**: SonarQube 系统（内网）

**漏洞描述**:
SonarQube 存在安全漏洞，攻击者可利用 API 设置值 URI，获取到明文的 SMTP 和 GitLab 凭证（token）等敏感信息。泄露的 GitLab user_token 可用于 clone 任意内部仓库代码，获取到的源代码可绕过内部安全审计，进一步从配置文件中获取数据库账号密码等。

**技术细节**:
- SonarQube 的某 API 端点未做充分的权限控制，普通用户可查看系统配置
- 配置中明文存储了 GitLab token 和 SMTP 凭证
- GitLab token 可执行 `git clone https://token@gitlab.example.com/repo.git` 拉取全量代码
- 源代码中通常包含更多凭证（数据库密码、第三方 API 密钥等），形成攻击链

**修复方案**:
升级 SonarQube 到最新版；对 SonarQube 配置 API 做严格的管理员权限控制；定期轮换已泄露的 GitLab token 和 SMTP 凭证。

**经验总结**:
日志文件不应记录密码、Token、身份证号等敏感信息；第三方开发工具（SonarQube、Jenkins 等）同样需要安全加固，不能默认信任内网环境。

### 案例4：某内部系统全量用户信息泄露（IDOR）
**系统**: 某内部系统

**漏洞描述**:
多个接口存在 IDOR 导致全量用户信息泄露：/user/v31/team/group_users（组内全量用户信息）、/user/v31/manage/user/list（管理员可见全量用户列表）、/user/v31/org/user/same_level_or_managed_org_user_list（同级/下属组织全量用户）、/user/v31/org/team/info（团队信息 IDOR）。通过修改请求中的 ID 参数，可越权获取任意组织/用户的详细信息。

**技术细节**:
- 四个接口均未校验请求者是否有权限访问目标 ID 对应的数据
- /user/v31/manage/user/list 为管理员接口，普通用户也可调用说明同时存在垂直越权
- 遍历 group_id 可系统性获取全量用户数据，形成信息泄露规模化攻击

**修复方案**:
参见 docs 文档漏洞总览第 1-4 点修复建议；对所有 list/detail 接口严格校验请求者权限，返回结果过滤到当前用户有权限访问的范围内。

**经验总结**:
Git 仓库不应提交 .env、配置文件、私钥等敏感文件，需定期扫描历史提交；用户管理类接口需同时检查水平越权（访问他人数据）和垂直越权（普通用户访问管理员接口）。

### 案例5：mojidoc 文档接力功能可查看任意用户手机号
**系统**: www.mojidoc.com

**漏洞描述**:
文档接力功能允许接力给空间外任意用户，而查看接力节点信息时可看到接力者的明文手机号。由于可以批量获取 userid（约 1786 个），理论上可通过接力操作枚举查看这 1786 个用户的明文手机号。

**技术细节**:
- 接力业务逻辑允许跨空间接力，接力对象不受空间成员限制
- 查看接力节点 API 响应中直接返回手机号明文，未做脱敏
- 两个业务逻辑缺陷叠加：可接力给任意用户 + 节点信息返回明文手机号
- 虽然 userid 不完全可遍历，但存量可枚举的 userid 已足够造成批量泄露

**修复方案**:
一是产品层面限制接力只能给同一空间内的用户；二是查看节点信息接口对明文手机号做脱敏处理（如 138****1234）。

**经验总结**:
分页接口如果通过遍历可以枚举用户信息，需对请求频率做限制；接口返回数据中凡含手机号、邮箱、身份证号等字段，必须做脱敏处理。

### 案例6：亲情卡接口可遍历查询用户手机号（account_id 与手机号双向枚举）
**系统**: 某支付/会员系统（亲情卡功能）

**漏洞描述**:
/pay/member/h5/product/family_card/query_user_info 接口支持通过手机号或 account_id 双向查询用户信息。由于 account_id 是公开可获取的，通过传入 account_id 可获取脱敏手机号；再通过传入手机号反查 account_id，构成双向枚举链路，可批量建立 account_id 与手机号的对应关系，导致大规模用户手机号泄露。

**技术细节**:
- account_id 为公开信息，可大量获取
- 接口同时支持 account_id → 脱敏手机号，以及 手机号 → account_id 两种查询方式
- 脱敏手机号（如 138****1234）配合枚举可进一步还原
- 接口无频率限制，可自动化批量查询

**修复方案**:
删除接口中返回的手机号字段；接口接入风控，限制查询频率；增加限制：手机号查询仅获取内部 eid，通过 eid 进行后续业务操作，不返回账号与手机号的对应关系。

**经验总结**:
敏感字段（手机号、邮箱、身份证）在列表接口中应做脱敏处理；双向查询接口需评估是否可构成枚举攻击链。

### 案例7：商家存量资质未接入防盗链（资质证件直链泄露）
**系统**: locallife-merchant-invest-center（本地生活商家入驻中心）

**漏洞描述**:
GetMerchantCertDetails 接口返回的商家资质图片（营业执照、身份证等）直链未接入防盗链保护，任何人获取到图片 URL 后即可直接访问下载，无需任何身份认证，存在商家敏感资质证件泄露风险。

**技术细节**:
- 商家资质包含营业执照、法人身份证等高度敏感文件
- 未使用时效性 URL（签名 URL / 防盗链）保护图片访问
- 一旦 URL 被泄露（如日志、分享等），资质图片将永久可被任意访问
- 存量历史数据同样受影响，需批量刷新 URL

**修复方案**:
存量数据刷数处理，为所有已生成的资质图片 URL 接入防盗链（带时效和签名的临时访问链接）；新增数据直接使用签名 URL 方案。

**经验总结**:
响应头不应泄露服务器版本、框架信息；文件存储（OSS/COS）中的敏感文件需使用时效性签名 URL，禁止使用永久公开直链。

### 案例8：UPS 网络管理卡 SNMP 敏感凭证未授权泄露
**系统**: UPS 网络管理卡 Web 管理界面

**漏洞描述**:
UPS 网络管理卡的 Web 管理界面中，/settings/snmp_configuration.html 接口未对访问请求进行鉴权校验，攻击者无需登录即可直接访问该页面，获取设备的 SNMP 配置内容，包括 SNMP v1/v2c 社区串（Community String），可用于读写 UPS 状态和配置。

**技术细节**:
- SNMP Community String 类似于明文密码，泄露后可直接读取/修改 UPS 配置
- SNMP write 权限可修改 UPS 参数，可能导致供电中断等物理安全事故
- 物联网/硬件设备的 Web 管理界面往往忽视身份认证
- UPS 设备通常接入核心基础设施，危害极高

**修复方案**:
对 /settings/snmp_configuration.html 及所有配置页面接口进行鉴权校验；实施网络隔离，UPS 管理界面仅允许运维网段访问，禁止公网可达。

**经验总结**:
搜索建议类接口可能泄露其他用户的私密信息；IoT/硬件设备的管理接口同样需要安全审计，不能因为是"内网设备"就忽视认证。

### 案例9：Kwai 商店卖家中心接口泄露用户邮箱
**系统**: Kwai 商店卖家中心

**漏洞描述**:
/rest/o/ecommerce/customer/author/getInviterInfo 接口的响应内容中包含用户的明文邮箱信息。邮箱属于用户个人敏感信息，接口在非必要情况下返回了该字段，违反最小必要原则。实际场景中用户通过该接口只能获取自己的邮箱（低危），但非必要的敏感字段暴露仍属设计缺陷。

**技术细节**:
- 接口响应包含 email 字段，该字段对调用方非必要
- 过度返回（Over-fetching）设计模式导致无意间暴露敏感字段
- 若接口存在 IDOR 漏洞，邮箱泄露风险将升级为高危

**修复方案**:
非必要情况不返回邮箱、手机号等敏感数据；如确需返回，对邮箱做脱敏处理（如 te***@gmail.com）。

**经验总结**:
前端打包的 sourcemap 文件不应在生产环境暴露；接口设计应遵循最小数据返回原则，定期审查响应体中是否包含非必要的敏感字段。

### 案例10：罗盘系统可无限制通过手机号抓取 KsUserId（无频率限制）
**系统**: 客户罗盘系统

**漏洞描述**:
某客户罗盘系统存在一个可通过手机号查询平台对应用户ID的接口，该接口未做任何频率校验。攻击者可生成全国三大运营商手机号码段，通过该接口批量提取平台中所有国内用户的用户ID，进而获取用户昵称、粉丝数等公开信息，造成大规模用户信息泄露。

**技术细节**:
- 手机号与 ksuserid 的对应关系属于隐私数据，不应允许批量枚举
- 接口无频率限制（rate limiting），可被自动化工具高速遍历
- 三大运营商手机号段（130-139、150-159、180-189 等）约 14 亿个号段，可系统性遍历
- 获取 ksuserid 后可进一步关联用户公开信息，形成完整用户画像

**修复方案**:
对接口进行频次访问限制（每账号/每 IP 每天不超过 N 次）；userid 信息不回显前端，后台自动绑定；排查该接口是否已有大量异常访问记录。

**经验总结**:
多环境配置需分离，测试环境密钥不应在生产使用；查询类接口需同时考虑：返回值是否敏感 + 是否有频率限制，两者缺一即构成信息泄露风险。

## 二、业界经典案例（乌云）

### 案例1：某信用卡 APP 运维不当——log4net 配置文件泄露数据库密码
**厂商**: 某信用卡 | **类型**: 敏感信息泄露（配置文件泄露）

**洞察**: 移动 APP 使用 log4net 记录日志，配置文件（log4net.config）部署在 Web 可访问目录，文件中包含数据库连接字符串（含明文密码 sa），攻击者可直接下载获取数据库凭证。

**测试流程**:
1. 访问 APP 相关 Web 服务目录，尝试常见配置文件路径
2. 猜测 .config/.xml 等后缀的配置文件（log4net.config、web.config 等）
3. 直接 GET 请求下载配置文件
4. 从文件中提取数据库连接字符串，获取明文密码

**技术细节**:
log4net.config 文件暴露在 Web 根目录，包含完整数据库连接字符串：`pwd=sa; initial catalog=test_log4net; persist security info=True`，明文密码可直接用于数据库登录。

**POC示例**:
```
GET /app/log4net.config HTTP/1.1
# 或
GET /web.config HTTP/1.1
# 响应包含:
# <commandText value="INSERT INTO Log...">
# <connectionString value="...;pwd=sa;">
```

**绕过技巧**: 无需绕过，直接 HTTP GET 请求即可获取配置文件。

**修复建议**: 配置文件禁止通过 Web 访问（Nginx 禁止 .config 文件访问）；数据库连接字符串加密存储；web.config 添加 `<location><system.web><authorization><deny users="*"/>`。

### 案例2：TOM 某分站 SVN 源码泄露（.svn/entries 暴露）
**厂商**: TOM在线 | **类型**: 敏感信息泄露（SVN源码泄露）

**洞察**: SVN 版本控制目录（.svn）被部署到 Web 根目录，攻击者可通过 /.svn/entries 获取文件列表，进而下载完整源代码，包含配置文件、数据库凭证等。

**测试流程**:
1. 访问 /.svn/entries 确认 SVN 目录是否暴露
2. 下载 /.svn/entries 获取项目文件列表
3. 按文件列表逐一下载源代码文件
4. 分析源码中的配置信息和安全漏洞

**技术细节**:
live4.sports.tom.com/.svn/entries 泄露完整 SVN 源码，可使用 dvcs-ripper 等工具自动化提取：`python rip-svn.py -v -u http://target/`，批量下载所有版本的源代码文件。

**POC示例**:
```
GET /.svn/entries HTTP/1.1
# 获取文件列表后逐一下载:
# 使用工具: python rip-svn.py -v -u http://target/
```

**绕过技巧**: SVN 元数据目录直接可访问，无需任何绕过技巧。

**修复建议**: 部署时使用 `svn export` 而非 `svn checkout`，排除 .svn/.git 目录；Web 服务器配置禁止访问以点开头的隐藏目录（Nginx: `location ~ /\. { deny all; }`）。

### 案例3：hitao 某系统 MongoDB 未授权访问——千万用户数据泄露并延伸 FTP 入侵
**厂商**: hitao（某电商） | **类型**: 敏感信息泄露（MongoDB未授权 + FTP凭证泄露）

**洞察**: MongoDB 未授权访问不仅泄露千万条用户数据，更在数据库中发现存储的 FTP 账号密码，利用该凭证可进一步登录文件服务器，形成"数据泄露 → 凭证利用 → 服务器入侵"完整攻击链。

**测试流程**:
1. 发现公网 MongoDB 服务（无认证）
2. 连接后枚举所有数据库，获取用户数据
3. 在 MongoDB 中搜索配置信息（config 集合）
4. 发现 FTP 账号密码，登录文件服务器进行进一步渗透

**技术细节**:
MongoDB 公网暴露无认证，包含千万条用户数据；数据库中存储了 FTP 服务器账号密码（凭证硬编码在数据库中），攻击者可利用泄露凭证横向移动至文件服务器。

**POC示例**:
```
mongo target_ip:27017
use userdb
db.users.find()
db.config.find()   # 查找 FTP/DB 配置信息
```

**绕过技巧**: MongoDB 默认无认证，直接访问；凭证链接可利用 db.config.find() 查找。

**修复建议**: MongoDB 强制认证（auth=true），禁止公网访问；凭证不存储在数据库中，使用专用密钥管理系统；防火墙限制 27017 端口。

### 案例4：7天连锁酒店 SSO 凭证泄露——跨系统未授权访问
**厂商**: 7天连锁酒店 | **类型**: 敏感信息泄露（SSO多系统凭证）

**洞察**: 酒店 IT 系统的 SSO 凭证泄露，由于单点登录系统打通了多个内部平台，单一凭证泄露可导致攻击者进入所有相关管理系统，危害倍增。

**测试流程**:
1. 通过某途径获取泄露的 SSO 凭证
2. 尝试使用凭证登录 SSO 系统
3. 通过 SSO 进入多个内部管理后台
4. 访问连锁酒店各类管理系统的敏感数据

**技术细节**:
SSO 系统凭证（mmxlhcx/*)*@#）通吃多个系统，一处泄露影响所有已接入 SSO 的内部平台，包括各类管理后台和运营系统。

**POC示例**:
```
使用泄露凭证尝试 SSO 登录:
POST /sso/login HTTP/1.1
username=mmxlhcx&password=)*@#
```

**绕过技巧**: 利用凭证重用，通过 SSO 系统横向访问所有已接入平台。

**修复建议**: SSO 系统使用强密码策略，密码定期强制更换；添加双因素认证（2FA）；凭证泄露后立即吊销并强制全平台下线。

### 案例5：某零食电商短信接口账号密码泄露——可查看所有验证码

**技术细节**:
SMS API 凭证泄露后，攻击者可查询任意手机号收到的短信验证码，用于登录、密码重置等操作，导致平台所有用户账号面临被接管风险。

```

**修复建议**: SMS API 密钥不得出现在前端代码或客户端；服务端代理所有短信请求，客户端只发送业务参数；验证码一次性使用且有时效（建议 5 分钟）。

### 案例7：某 K 歌 APP 接口响应含服务器配置信息——导致服务器沦陷

**洞察**: APP 的 HTTP API 响应中包含服务器内部配置信息（数据库地址、账号密码等），通过中间人抓包即可直接获取，攻击者利用泄露信息成功攻击后端服务器。

**测试流程**:
1. 使用 Charles/Burp Suite 代理抓取 APP 的 HTTP 请求和响应

3. 提取数据库连接信息
4. 直接连接数据库服务器或利用信息进一步攻击

**技术细节**:
APP API 响应中直接包含数据库连接信息（db_host、db_user、db_password），通过 HTTP 流量分析即可获取，导致攻击者绕过应用层直接攻击数据库，服务器被完全控制。

#   "db_password": "xxxxx"
# }
```

**绕过技巧**: 中间人抓包，无需特殊技术绕过，APP 明文传输敏感配置。

**修复建议**: API 响应严格遵循最小数据原则，只返回业务需要的字段；服务器配置信息绝不出现在 API 响应中；强制使用 HTTPS 防止中间人流量截获。

### 案例8：致远协同 OA 系统日志泄露 Session——任意用户登录
**厂商**: 致远协同OA系统 | **类型**: 敏感信息泄露（Session日志泄露）

**洞察**: OA 系统日志文件通过 Web 路径可直接访问，日志中包含大量用户的 Session ID（JSESSIONID），攻击者获取 Session ID 后即可直接冒充合法用户身份登录系统，还可查看上亿元资金台账信息。

**测试流程**:
1. 访问 /seeyon/logs/ctp.log 确认日志文件可读
2. 从日志内容中提取有效的 JSESSIONID
3. 将 Session ID 添加到 Cookie 发送请求
4. 以合法用户身份访问系统，获取资金台账等敏感信息

**技术细节**:
/seeyon//logs/ctp.log 日志文件对外可访问，包含大量用户 Session；日志记录了完整的 JSESSIONID，攻击者复用 Session 即可实现身份冒充。

**POC示例**:
```
GET /seeyon/logs/ctp.log HTTP/1.1
# 从日志中提取: JSESSIONID=XXXXXXXX

# 然后使用提取的 Session 访问系统:
GET /seeyon/main.do HTTP/1.1
Cookie: JSESSIONID=XXXXXXXX
```

**绕过技巧**: 直接复用日志中记录的有效 Session ID，无需登录。

**修复建议**: 日志文件禁止通过 Web 路径访问（Nginx 限制 /logs/ 目录）；日志中对 Session ID 等敏感信息做掩码处理（如只记录前 8 位）；Session 有效期设置合理的超时时间。

### 案例11：某安全厂商 ADS 抗 DDoS 系统存在 Heartbleed 漏洞（CVE-2014-0160）
**厂商**: 某安全厂商 | **类型**: 敏感信息泄露（CVE-2014-0160 Heartbleed）

**洞察**: 安全厂商自身产品（ADS 抗 DDoS 系统）存在 Heartbleed 漏洞，可通过构造恶意 TLS 心跳包读取服务器内存中的 SSL 私钥、Session、密码等敏感信息，讽刺性地证明了"安全产品"同样需要安全审计。

**测试流程**:
1. 使用 heartbleed 检测工具探测目标 HTTPS 服务
2. 发送构造的恶意 TLS HeartbeatRequest（长度字段伪造）
3. 读取服务器返回的内存数据（每次最多 64KB）
4. 从内存数据中提取 SSL 私钥、用户密码、Session Cookie 等

**技术细节**:
OpenSSL 1.0.1a-1.0.1f 存在 Heartbleed 漏洞（CVE-2014-0160），某安全厂商 ADS 抗 DDoS 设备同样使用受影响版本，可被利用读取服务器内存中的敏感信息。

**POC示例**:
```
# 使用 heartbleed 检测工具:
python heartbleed.py target_ip
# 或使用 ssltest.py 检测
# 发送恶意心跳包读取内存数据 (每次最多 64KB)
```

**绕过技巧**: TLS 协议层漏洞，无需绕过应用层防护；安全设备自身存在漏洞，传统 WAF 无法防护。

**修复建议**: 升级 OpenSSL 到 1.0.1g+ 或 1.0.2+；修复后重新生成 SSL 证书和私钥；吊销所有旧证书并通知 CA；强制所有用户重新登录（使历史 Session 失效）。

## 三、方法论总结

### 3.1 高频参数统计

| 参数/字段名 | 出现频次 | 泄露内容 |
|-------------|----------|----------|
| token / x-auth-token | ★★★★★ | 认证凭证，泄露可直接冒用身份 |
| phone / mobile | ★★★★★ | 手机号，可用于账号关联与枚举 |
| email | ★★★★ | 邮箱地址，可用于账号登录 |
| password / pwd | ★★★★ | 明文密码，直接造成账号沦陷 |
| JSESSIONID / session_id | ★★★★ | 会话标识，复用可冒充登录状态 |
| orderId / account_id | ★★★ | 业务 ID，遍历可获取大量用户信息 |
| db_host / db_password | ★★★ | 数据库凭证，直接攻击后端服务 |
| api_key / api_secret | ★★★ | 第三方服务密钥，可冒用平台资源 |

### 3.2 攻击模式分布

| 攻击模式 | 案例数 | 典型代表 |
|----------|--------|----------|
| 配置文件/源码直接暴露 | 5 | SVN/Git 目录、web.config、备份 zip、log4net.config |
| 日志文件泄露敏感信息 | 3 | OA Session 日志、KIM SDK token 日志、APP 接口响应 |
| 接口响应过度返回 | 4 | 邮箱字段、手机号、数据库配置、ksuserid 映射 |
| 第三方服务凭证泄露 | 3 | SMS API 密钥、GitLab token、SSO 凭证 |
| 基础设施未授权访问 | 2 | MongoDB 无认证、SNMP 配置未鉴权 |
| 协议层漏洞 | 1 | Heartbleed CVE-2014-0160 |

### 3.3 关键检测信号

**高危信号（立即告警）**:
- Web 目录下存在 .svn/.git 目录（访问 /.svn/entries 有响应）
- 接口响应中包含 password/pwd/secret/token 等字段
- 日志文件通过 HTTP 路径可访问（/logs/*.log）
- GitHub/GitLab 公开仓库中含有公司域名邮箱和密码的代码
- MongoDB/Redis 端口（27017/6379）对公网开放且无认证

**中危信号（人工审核）**:
- 接口响应包含手机号、邮箱、身份证号等敏感字段且未脱敏
- 配置文件（.config/.env/.xml）在 Web 目录可访问
- Web 目录下存在 .zip/.tar.gz/.bak 等备份文件
- API 响应包含服务器版本、内部路径等调试信息
- 接口可通过遍历 ID 枚举其他用户信息

**低危信号（周期巡检）**:
- 接口返回非必要的用户敏感字段（如邮箱、完整手机号）
- 生产环境 sourcemap 文件可访问
- 响应头包含 X-Powered-By、Server 版本信息
- OSS/COS 敏感文件使用永久公开直链而非时效签名 URL

### 3.4 常见绕过技巧

1. **直接路径访问**: 配置文件、日志文件、备份文件、.svn/.git 目录无需任何绕过，直接构造 URL 访问即可。常用路径：`/.svn/entries`、`/web.config`、`/backup.zip`、`/logs/app.log`。

2. **GitHub 关键词搜索**: 使用 `site:github.com 公司域名 password/secret/token` 等关键词在 GitHub 搜索泄露凭证，利用开发者无意识的公开提交。

3. **接口响应分析**: 使用代理工具（Burp Suite/Charles）拦截 APP 或 Web 请求，系统性分析每个响应体中是否包含非必要的敏感字段，特别关注 user/profile/config 类接口。

4. **连续 ID 遍历**: 发现 orderId、userId、applyCode 等连续数字参数后，通过自动化脚本顺序遍历，批量获取全量数据。

5. **数据库服务直连**: 发现 MongoDB（27017）、Redis（6379）、MySQL（3306）等数据库端口对外开放时，尝试无密码直接连接，枚举数据库和集合。

6. **凭证复用与链接攻击**: 从一处泄露的凭证出发，尝试登录其他系统（邮箱、VPN、内部平台），利用人员密码复用习惯横向移动。

7. **Session/Token 复用**: 从日志文件、URL 参数、Referer 头等处收集历史 Session 并尝试复用；JWT Token 可解码分析有效期和声明内容。
